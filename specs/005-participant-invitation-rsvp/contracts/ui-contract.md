# UI 契約：參與者邀請與出席回覆

**功能分支**：`005-participant-invitation-rsvp`

## 共用約定

- 路由：hash 路由。本功能新增 `#/invitations`（我的邀請列表）與 `#/invitations/:invitationId`（邀請詳情）；不新增預約詳情路由，預約詳情的受邀者面板掛在沿用 001 的 `#/bookings`（我的預約）每筆單次預約卡片上，展開後顯示。UI-01 在沿用 001 的 `#/bookings/new`（單次預約，勾選「重複預約」後為週期性）與 002 的 `#/bookings/new?from={預約識別}`（再預約一次）上增加「邀請同事」欄位；`#/bookings/:bookingId/edit`（修改預約）、週期性預約與登記候補對話框不提供此欄位。UI-04 在沿用 001 的 `#/notifications` 上增加五種邀請通知。其餘路由（`#/login`、`#/venues`、`#/waitlist` 等）沿用 001～004，不在本契約範圍。
- 本功能的範圍：只增加「預約時邀請同事」「受邀者查看與回覆邀請」「預約者查看受邀名單與出席統計」「新增與移除受邀者」「邀請通知」。預約規則、預約送出流程、被拒絕時的規則清單、修改預約、再預約一次、站內通知的既有行為一律沿用，本功能不複製、不修改任何預約規則。邀請只屬於單次預約；週期性預約與候補遞補確認沒有邀請。
- 導覽列：登入後每頁顯示導覽列（`[data-testid="app-nav"]`）；桌機寬度（768 像素以上）固定於畫面左側成為側欄，低於 768 像素時改為頂部列並以「選單」按鈕（`[data-testid="app-nav-toggle"]`）展開。本功能在「我的預約」之後新增導覽項目「我的邀請」（`[data-testid="app-nav-invitations"]`），所有登入員工都顯示；我的邀請頁與邀請詳情的導覽高亮項目為「我的邀請」，預約表單與我的預約的高亮項目為「我的預約」，通知頁為「通知」。導覽項目依角色顯示只是方便，授權以內層為準。
- 路由守衛：未登入開啟任何頁面時導向 `#/login`，登入成功後回到原本要前往的頁面（含從邀請通知連結進入的邀請詳情）；帳號被標示為須先改密碼時，除 `#/change-password` 與登出外的所有路由一律導向 `#/change-password`。
- 目前使用者：本功能的介面都需要「目前使用者」（識別、姓名、Email、角色、預約權限暫停解除時間）。預約權限暫停期間，預約表單頂部顯示暫停提示（`[data-testid="suspension-banner"]`）；暫停不影響受邀者回覆邀請，也不影響預約者查看或調整自己預約的受邀者。
- 「現在」的來源：與「現在」有關的判斷（預約是否已開始、是否仍可回覆、是否仍可新增或移除受邀者）一律由內層判定並隨資料提供，前端不以裝置時鐘判斷，也不顯示倒數計時，一律顯示絕對時間。
- 隱私與授權界線（NFR-006）：受邀者的畫面（我的邀請、邀請詳情、邀請通知）只顯示預約者姓名、場地名稱與地點、日期、起訖時間、主題與自己的回覆，不顯示預約人數、其他受邀者與他們的回覆；受邀名單與出席統計只出現在預約者自己的預約卡片上。前端不推測、不快取他人的邀請或名單；略過畫面直接存取被內層拒絕時，前端只顯示「找不到這份邀請」或「沒有權限」類的一般訊息，不顯示任何他人資料。授權以內層為準。
- 出席統計界線（FR-016）：受邀者面板只顯示人數，不顯示任何「建議改小場地」的提示、不推薦場地、不自動修改預約的場地、人數或時間；想改場地時使用 001 的「修改」。前端不自行計算統計，受邀人數、已接受、已婉拒、未回覆與預計到場人數一律顯示內層回傳的值。
- 邀請狀態與回覆狀態的顯示名稱：邀請狀態固定為「待發送」「有效」「已失效」，其中「有效」的邀請另有回覆狀態「未回覆」「已接受」「已婉拒」；畫面上「已失效」的邀請標示「邀請已失效」並保留最後的回覆。邀請狀態與回覆狀態的代碼由後端介面文檔定義，本契約以中文名稱指稱；前端實作時依後端介面文檔的代碼判斷畫面行為，不依中文文字判斷。這兩組狀態不屬於 C-SH-01 的預約狀態代碼，不得與預約狀態代碼混用。
- 時間顯示（C-SH-02）：畫面上的時間一律以台北時間（UTC+8）顯示、不隨裝置時區改變，且時間輸入只送出台北當地的日期與時分，不含時區或偏移量。內層提供的時間點為帶 `Z` 的 ISO 8601 UTC 字串，前端換算為台北時間後顯示，不使用裝置時區。日期格式為「{YYYY}年{M}月{D}日（週{X}）」，時間為 24 小時制 `HH:mm`，起訖寫成 `HH:mm–HH:mm`；結束時間正好是台北當天結束時寫成 `24:00`。預約表單在時間欄位旁提示「時間以台北時間（UTC+8）顯示」。本功能自己的畫面沒有時間輸入欄位；邀請列表、邀請詳情、受邀者面板與邀請通知內的日期與起訖都依此格式顯示。
- 預約狀態代碼（C-SH-01）：預約狀態以英文 snake_case 代碼指稱，與後端、資料庫逐字相同；中文只作顯示文案，對應如下表。畫面依預約狀態決定行為（受邀者能否回覆、預約者能否調整受邀者、是否顯示預計到場人數）時一律依代碼判斷，不依中文文字判斷；狀態標籤的 `data-status` 屬性帶代碼；畫面上只顯示中文文案，不顯示代碼。

  | 代碼         | 顯示文案 |
  | ------------ | -------- |
  | `pending`    | 待審核   |
  | `confirmed`  | 已確認   |
  | `checked_in` | 已報到   |
  | `completed`  | 已完成   |
  | `rejected`   | 已駁回   |
  | `cancelled`  | 已取消   |
  | `no_show`    | 未到場   |

- 訊息語言：繁體中文（`<html lang="zh-Hant-TW">`）。所有失敗訊息說明「發生什麼事」與「可以怎麼做」，不顯示內部規則代碼、錯誤代碼、堆疊或技術細節。
- 定位屬性：以 `data-testid` 標示介面與可操作元素。介面的狀態區塊定位為該介面定位值加上後綴：載入 `-loading`、空狀態 `-empty`、錯誤 `-error`。各操作的元素定位寫在操作欄「操作」名稱後的括號內；列表項目的識別以 `data-id` 屬性標示（邀請識別、受邀者的邀請識別、預約識別）。表單欄位的欄位錯誤訊息定位為欄位定位加 `-error`，欄位的輔助說明定位為欄位定位加 `-hint`。沿用 001～004 的定位不變，原型中出現者包含：預約表單的 `booking-form`、`booking-venue`、`booking-date`、`booking-start`、`booking-end`、`booking-subject`、`booking-attendees`、`booking-venue-info`、`booking-recurring-toggle`、`booking-submit`、`booking-back`、`booking-result`、`booking-go-my-bookings`、`booking-form-error`、`booking-rebook-notice`、`booking-rebook-general-link`、`booking-form-loading`、`suspension-banner`；我的預約的 `my-bookings`、`my-bookings-tab-upcoming`、`my-bookings-tab-past`、`my-bookings-list`、`my-bookings-item`；通知的 `notification-page`、`notification-summary`、`notification-list`、`notification-item`、`notification-open`、`notification-load-more`、`app-notification-badge`；導覽與提示的 `app-nav`、`app-nav-toggle`、`app-nav-venues`、`app-nav-bookings`、`app-nav-notifications`、`app-change-password`、`app-logout`、`app-forbidden`、`app-toast`。
- 回饋時限：點擊或送出後 200 毫秒內出現可見回饋（按鈕停用並顯示處理中文字）。可點的控制項在送出前即停用，避免重複送出（NFR-001、NFR-002、NFR-004）。
- 版面（NFR-007）：桌機寬度 768 像素以上為多欄版面；低於 768 像素為單欄，卡片與按鈕換行排列；寬度 360 像素時，邀請欄位、我的邀請列表與詳情、受邀者面板（統計、名單、新增與移除）與邀請通知的內容都不得需要水平捲動才能操作；Email 與姓名等長文字在容器內自動換行，不撐開版面。
- 無障礙：每個欄位都有可見標籤；錯誤訊息容器使用 `role="alert"`；載入區使用 `aria-busy="true"`；對話框使用 `<dialog>` 並有名稱，開啟後焦點移入、關閉後焦點回到觸發元素，Esc 可關閉；邀請狀態、回覆狀態與預約狀態不只靠顏色，一律同時顯示文字標籤；可點目標至少 44 像素高。
- 提示訊息：操作成功或失敗的頁面提示定位為 `[data-testid="app-toast"]`，失敗提示 `role="alert"`，成功提示 `role="status"`。

## UI-01 預約表單邀請同事介面（多個 Email 輸入欄位、有問題的 Email 與原因、僅單次預約與再預約顯示、再預約空白、週期性勾選與修改預約時不顯示）

**路由**：`#/bookings/new`（單次預約，可帶場地、日期、起訖參數）、`#/bookings/new?from={預約識別}`（再預約一次）；勾選「重複預約」、`#/bookings/:bookingId/edit` 與登記候補對話框不顯示本欄位
**定位**：`[data-testid="booking-form"]` 內的 `[data-testid="booking-invitees"]`

### 操作

| 操作 | 互動 | 需要內層提供 |
| ---- | ---- | ------------ |
| 看見邀請同事欄位（`booking-invitees`、`booking-invitees-hint`） | 單次預約表單（含再預約）在主題與人數之後顯示選填的「邀請同事」欄位，預設一列空白的 Email 輸入欄位，欄位下方說明「選填。受邀同事需有啟用中的帳號；受邀人數不受預約人數與場地容納人數限制。」。週期性預約（勾選「重複預約」）、修改預約與登記候補對話框不顯示本欄位 | 無（是否為單次、修改或再預約模式由網址與勾選狀態判定，前端自行判斷） |
| 填寫受邀 Email（`booking-invitee-input`） | 每列一個 Email 輸入欄位；輸入時不逐字檢查，失焦時只檢查格式（須為 Email 格式），格式不符在該列下方顯示錯誤；貼上含多個 Email 的文字（以逗號、空白或換行分隔）時自動拆成多列；前後空白不計。是否有對應帳號、是否停用、是否為自己，前端不判斷，送出後由內層判定。重複填寫的 Email（不分大小寫、忽略前後空白）顯示「重複的 Email 只會邀請一次。」（`booking-invitees-duplicate`），不算錯誤、不阻擋送出 | 無（送出前不查詢帳號） |
| 新增與移除欄位（`booking-invitee-add`、`booking-invitee-remove`） | 按「新增一位」增加一列；每列右側有「移除」按鈕（只剩一列時清空該列內容而不刪除該列）；欄位數量不設上限；欄位下方顯示「將邀請 {人數} 位同事」（不含空白列與重複者）（`booking-invitees-count`） | 無 |
| 再預約時為空白（`booking-invitees-rebook-note`） | 由「再預約一次」開啟時，Email 欄位為一列空白，不帶入來源預約的受邀者，並在欄位下方說明「再預約不會帶入上次的受邀者，需要的話請重新填寫。」 | 無（再預約模式的來源預約資料沿用 002，不含受邀者） |
| 勾選「重複預約」時隱藏並清空（`booking-recurring-toggle`、`booking-invitees-cleared`） | 勾選後本欄位隱藏，已填的 Email 全部清空，並以提示說明「週期性預約不支援邀請同事，已填的 Email 已清除。」（`role="status"`）；取消勾選回到單次預約時，欄位重新出現且為一列空白 | 無 |
| 送出預約帶入受邀 Email（`booking-submit`） | 沿用 001 的「送出預約」，同一次送出包含所有非空白的 Email；送出後按鈕停用並顯示「送出中…」，欄位停用，避免重複送出（NFR-001）。成功後沿用 001 的結果面板（`booking-result`），並附上邀請說明句（`booking-result-invitees`）：預約為 `confirmed` 時說明已發送邀請的人數；為 `pending` 時說明「核准後才會發送邀請」；沒有填 Email 時不顯示邀請說明句 | 建立單次預約（場地、日期、起訖、主題、人數、受邀 Email 清單）的結果：成立並回傳預約狀態（`confirmed`／`pending`）與受邀人數（去除重複後）；或受邀 Email 未通過驗證，回傳每個有問題的 Email 與原因（查無帳號、帳號已停用、不能邀請自己），此時不建立預約與任何邀請；或其他未通過的規則清單（沿用 001） |
| 顯示有問題的 Email 與原因（`booking-invitees-error`、`booking-invitees-problem-item`、`booking-invitee-input-error`） | 受邀 Email 未通過驗證時，預約不成立；欄位區上方顯示錯誤清單「預約沒有成立。以下 Email 有問題，請修正或移除後再送出：」，每項為「{Email}：{原因}」；有問題的那一列同步標示錯誤並以 `aria-invalid="true"` 連到該項說明；焦點移到清單；表單已填的所有內容（含所有 Email）保留。有效 Email 的同事也不會收到邀請，清單中不列有效者 | 同上（有問題的 Email 與原因） |
| 其他規則被拒絕時保留 Email（`booking-form-error`） | 因時段被占用等 001 的規則被拒絕時，沿用 001 在表單頂部顯示規則清單，所有受邀 Email 保留在欄位中，沒有任何邀請被建立 | 同上（沿用 001 的規則清單） |

### 狀態

| 狀態 | 呈現 |
| ---- | ---- |
| 成功 | 邀請同事欄位顯示已填的 Email 列與「將邀請 {人數} 位同事」；送出後依預約狀態代碼顯示結果面板與邀請說明句（`confirmed`：已發送邀請；`pending`：核准後才發送） |
| 載入 | 沿用 001：載入場地時欄位位置顯示骨架（`booking-invitees-loading`），`aria-busy="true"`，送出按鈕停用；送出時按鈕顯示「送出中…」，欄位停用 |
| 空狀態 | 沒有填任何 Email 是正常情況，不是錯誤：顯示一列空白欄位與說明「沒有邀請任何人也可以送出。」（`booking-invitees-empty`），送出後預約照 001 成立，不顯示邀請說明句 |
| 錯誤 | 受邀 Email 未通過驗證：顯示有問題的 Email 與原因清單，預約不成立、表單內容保留；Email 格式不符：該列下方顯示「請輸入有效的 Email。」並攔截送出；其他規則被拒絕：沿用 001 的規則清單；送出失敗（網路或其他原因）：表單頂部顯示「無法送出預約，預約與邀請都沒有建立。請稍後再試一次。」，內容保留、按鈕恢復可用 |

## UI-04 邀請通知介面（邀請、變更、取消、移出邀請與開始前提醒五種通知的呈現、連到邀請詳情、已讀）

**路由**：`#/notifications`；未讀數徽章顯示於所有頁面的導覽列（沿用 001）
**定位**：`[data-testid="notification-page"]`

### 操作

| 操作 | 互動 | 需要內層提供 |
| ---- | ---- | ------------ |
| 看到五種邀請通知（`notification-list`、`notification-item`、`notification-type-tag`） | 通知列表沿用 001 由新到舊排列，除既有類型外，新增五種類型標籤：「收到邀請」「邀請變更」「邀請取消」「移出邀請」「受邀提醒」；每則顯示類型標籤、內容、發送時間與已讀狀態。內容由內層提供：收到邀請含預約者姓名、場地、日期、起訖時間與主題；邀請變更依內容分為時間變更（含新日期時間與新場地、說明回覆已重置請重新回覆）與只換場地（含新場地、說明回覆維持不變）；邀請取消含場地、日期、起訖時間，有取消原因時附上原因；移出邀請含場地、日期與起訖時間；受邀提醒含預約者姓名、主題、場地與開始時間 | 目前使用者的通知分頁列表，除 001 的欄位外，邀請相關通知附：通知類型（收到邀請、邀請變更、邀請取消、移出邀請、受邀提醒）、通知內容、相關邀請識別；受邀者本人的通知，預約者不會收到受邀者回覆產生的任何通知 |
| 開啟通知並標為已讀（`notification-open`） | 沿用 001：點選一則通知展開完整內容並標記為已讀，未讀數同步減少 | 標記該則通知為已讀（通知識別）；最新未讀數 |
| 從通知進入邀請詳情（`notification-open-invitation`） | 展開的邀請相關通知顯示「查看邀請」連結，點選前往 `#/invitations/:invitationId`，詳情可直接回覆；邀請已失效時（取消、移出邀請等）連結仍可進入，詳情顯示「邀請已失效」與最後的回覆 | 通知所屬的邀請識別 |
| 查看未讀數（`app-notification-badge`） | 沿用 001：導覽列徽章顯示未讀數，每 30 秒更新一次；頁面在背景時暫停更新，回到前景時立即更新一次 | 目前使用者的未讀通知數 |

### 狀態

| 狀態 | 呈現 |
| ---- | ---- |
| 成功 | 通知列表，未讀通知有「未讀」標籤與粗體標題，已讀通知為一般樣式；邀請相關通知多一個類型標籤與「查看邀請」連結；導覽列徽章顯示未讀數 |
| 載入 | 列表位置顯示骨架列（`notification-page-loading`）；開啟單則通知時，該則顯示處理中並暫不改變已讀樣式直到成功 |

| 錯誤 | 載入失敗顯示「重新載入」（`notification-page-error`）；標記已讀失敗時保留未讀樣式並提示稍後再試，仍展開內容與「查看邀請」連結；未讀數更新失敗時保留上次的數字，不打斷使用者；連結的邀請找不到時，由 UI-02 的詳情錯誤狀態處理 |
