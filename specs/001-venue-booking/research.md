## R-01 執行環境與語言版本

- **對應需求**：跨領域
- **決策**：Node.js 24 LTS（前後端工具鏈都使用），JavaScript（ES Modules、語法停在 ES2024），MySQL 8.4 LTS 以上。不使用 TypeScript，原始碼不另接轉譯器。
- **理由**：這是使用者指定的參考環境（Node.js 24、JavaScript、MySQL），開發機實測也是 Node.js 24（`v24.21.0`），nodejs.org 發布索引在 2026-10-27 把 24.22.2 標為 LTS（代號 Krypton）。Node.js 24 內建 `node:test`、`node:crypto`（含 `scrypt`）、`fetch` 與 `--env-file`，後續決策（見 R-03、R-04、R-17、R-18）因此幾乎不需要額外套件。MySQL 8.4 是 LTS 系列，支援 `SELECT ... FOR UPDATE SKIP LOCKED`、觸發器的 `SIGNAL` 與 `CHECK` 約束，這些是 R-07、R-09、R-10 的基礎。
- **已知限制**：MySQL 8.0 已於 2026 年 4 月前後結束延伸支援，這個日期來自第三方文章，尚未對照 Oracle 官方生命週期頁，待驗證；即使日期有出入，8.4 LTS 仍是較新的長期支援線，不影響這項決策。
- **考慮過的替代方案**：Node.js 26 自 2026-10-28 起也是 LTS（發布索引標示 Lithium），`@cucumber/cucumber` 13 的引擎範圍涵蓋 26，日後可升級；本次不採用，因為使用者指定的參考環境與開發機都是 24。MySQL 8.0 是參考範例使用的版本線，但已過延伸支援，所以改用 8.4。TypeScript 需要編譯步驟，與參考環境的純 JavaScript 不符。

## R-02 後端 HTTP 伺服器與 API 慣例

- **對應需求**：NFR-006、NFR-012、NFR-015、FR-052、FR-068、FR-069
- **決策**：使用 Node 內建的 `node:http`，同一個行程聽 `PORT`（預設 `3000`），自行撰寫路由器，支援 `:id` 形式的路徑參數（啟動時把路徑樣板編譯成正規表示式，方法加路徑精確比對）。慣例如下，細部路徑與欄位由 system-analysis 的介面文檔定義：
  1. 所有 API 在 `/api` 底下，請求與回應皆為 JSON，請求本文上限 100 KB。報表匯出是唯一例外，回應為 `text/csv`（見 R-14）。
  2. 狀態碼：`400` 格式或規則驗證未通過、`401` 未登入、`403` 無權限（含必須先改密碼，見 R-04）、`404` 資源不存在、`409` 衝突（時段被占用、已被處理、額度已達上限）。錯誤回應只有 `{ "message": "..." }`，訊息用繁體中文說明發生什麼事與可以怎麼做，不含內部代碼與堆疊（NFR-015）。
  3. 路由器只做比對與呼叫；驗證登入、授權（見 R-05）與交易邊界都在服務層，每個請求最多開一個資料庫交易。
  4. 需要「列出影響再確認」的操作（設定維護時段、停用場地、停用帳號、週期性預約衝突）採兩段式：預覽端點只回傳受影響的項目，不寫入；確認端點必須帶上使用者看過的項目 id 清單，伺服器在交易內重新計算，清單不一致就 `409` 並回傳最新清單，不取消使用者沒看過的預約。
  5. 非 `/api` 的 GET 在正式環境提供 `frontend/dist` 的靜態檔（見 R-16）。
- **理由**：端點數量固定，路由器是純函式，可以用 `node:test` 直接測試。兩段式確認讓 FR-068 的「管理員確認後才取消」在兩次請求之間有人新增預約時也不會誤傷：確認時重新計算，與使用者看過的清單比對。交易邊界集中在服務層，R-07、R-08 的鎖順序才能一致。
- **考慮過的替代方案**：Express 只為路由多一個相依套件，效益不高。Fastify 的外掛與結構驗證在這個規模用不到。

## R-03 後端執行期相依套件（共 1 個）

- **對應需求**：跨領域
- **決策**：後端執行期只引入下表 1 個套件，其餘使用 Node 內建模組。

| 套件             | 用途                                               | 為何無法用內建功能取代     |
| ---------------- | -------------------------------------------------- | -------------------------- |
| `mysql2@^3.24.0` | MySQL 驅動（`mysql2/promise`、連線池、預備陳述式） | Node 沒有內建 MySQL 用戶端 |

- **理由**：密碼雜湊用 `node:crypto` 的 `scrypt`（見 R-04），排程用 `setInterval`（見 R-10），CSV 用自寫序列化（見 R-14），HTTP 與路由用 `node:http`（見 R-02）。需求沒有即時推播（站內通知以輪詢取得，見 R-13），所以不需要 WebSocket 套件。`mysql2` 為純 JavaScript、沒有原生附加元件，2026-11-07 查 npm 的最新版是 3.24.6。
- **考慮過的替代方案**：`bcrypt` 與 `argon2` 都含原生附加元件，安裝時需要編譯或預建二進位檔，而 `scrypt` 已內建於 Node。`node-cron` 與 `node-schedule` 只提供時間觸發，但本系統的觸發條件來自資料庫狀態（見 R-10），用不到。CSV 套件對固定欄位的報表來說是多餘的相依。

## R-04 帳號、密碼與階段憑證

- **對應需求**：FR-001、FR-002、FR-003、FR-004、FR-005、NFR-001、NFR-012、US1
- **決策**：
  1. 帳號表以 Email 識別。儲存與比對前一律去除首尾空白並轉小寫，欄位加 `UNIQUE`，所以大小寫不同的同一信箱視為重複（FR-001）。角色放在 `user_roles`，一個帳號可有多個角色；所有帳號都隱含一般員工能力（FR-002）。
  2. 密碼以 `node:crypto` 的 `scrypt` 雜湊：成本參數 N=131072（2 的 17 次方）、r=8、p=1，金鑰長度 64 位元組，`maxmem` 設為 256 MiB，每個密碼使用 16 位元組隨機鹽，驗證用 `timingSafeEqual`。資料庫只存「參數、鹽、雜湊」的字串，沒有可還原的密碼（NFR-001）。密碼長度需為 8 到 128 個字元。
  3. 登入時，找不到帳號也要對一個固定的假雜湊執行一次 `scrypt`，讓兩種失敗的回應時間接近；帳號或密碼錯誤統一回應「Email 或密碼錯誤」。只有密碼驗證通過後才檢查停用狀態，停用帳號回應「帳號已停用」（FR-003）。
  4. 登入成功後用 `randomBytes(32)` 產生階段憑證，cookie 名稱 `sid`，內容只有這 64 個十六進位字元，屬性為 `HttpOnly`、`SameSite=Lax`、`Path=/`，在 TLS 或 `X-Forwarded-Proto: https` 時加 `Secure`。`sessions` 表只存憑證的 SHA-256（`token_hash`，`UNIQUE`）、帳號 id 與 `expires_at`；閒置 12 小時過期，每次使用往後延長。停用帳號、重設密碼與變更密碼時，刪除該帳號所有階段。
  5. 帳號有 `must_change_password` 旗標。管理員重設密碼時設為 1；為 1 時，除了「查詢自己、變更密碼、登出」以外的 API 一律 `403`，訊息為「請先設定新密碼」。變更密碼成功時清除旗標（FR-004）。登入頁面不提供忘記密碼的自助流程。
  6. 沒有註冊端點。第一位管理員由啟動指令建立（見 R-18）。
  7. 非 GET 請求必須是 `Content-Type: application/json`，且 `Origin` 標頭存在時必須屬於 `ALLOWED_ORIGINS`（開發預設 `http://localhost:5173`），否則 `403`。
- **理由**：規格要求 Email 加密碼登入（FR-003）且不得顯示密碼（NFR-001），雜湊加鹽即可滿足。`HttpOnly` cookie 不會被頁面腳本讀取，資料庫洩漏時也拿不到可直接重放的憑證。登入失敗的統一訊息與時間對齊對應 FR-003「不透露是哪一項錯誤」。`must_change_password` 讓 FR-004 的「首次登入先改密碼」由伺服器強制，而不是只靠畫面導向。
- **已知限制**：scrypt 參數取自 OWASP 密碼儲存備忘單列出的等效最低組合之一，上線前需在實際主機量測單次登入耗時與記憶體，待驗證；參數寫在雜湊字串內，之後調整不會讓舊密碼失效。
- **考慮過的替代方案**：把憑證放在 `localStorage` 會讓頁面腳本讀到它。JWT 無法在停用帳號時立即撤銷，每次仍要查資料庫確認狀態，沒有比階段表簡單。

## R-05 授權檢查

- **對應需求**：FR-002、FR-005、FR-007、FR-033、FR-035、FR-070、FR-072、FR-084、NFR-002、NFR-012、NFR-013、SC-007
- **決策**：授權集中在純函式 `backend/src/domain/policy.js`，簽名為 `can(user, action, resource)`，回傳布林值。每個服務函式在動資料庫之前先呼叫它；沒有通過就 `403`。規則如下：
  1. 管理員專屬動作：帳號、場地、維護時段、規則、報表、查看所有預約與操作紀錄、直接取消預約（FR-072）。
  2. 員工只能對 `booking.user_id` 等於自己的預約做修改、取消、報到（FR-002 的一般員工能力）。查詢預約的 SQL 同時帶 `AND user_id = :userId`，所以即使漏了策略檢查也讀不到他人的預約。
  3. 場地需要審核時必須在 `venue_reviewers`（`venue_id`、`user_id`）至少有一位審核者，儲存場地時由服務層檢查（FR-007）。審核者只能審核 `venue_reviewers` 中指派給自己的場地；申請者就是審核者本人時拒絕，改由同場地其他審核者，沒有其他審核者時由管理員（FR-035）。
  4. 行事曆與場地搜尋的回應，對非管理員一律不帶預約者與主題欄位（NFR-002）；站內通知的查詢一律帶 `user_id = 目前使用者`（NFR-013）。
  5. 預約權限暫停（`users.suspended_until` 大於目前時間）時，建立預約、週期性預約、登記與確認候補被拒絕（FR-043 的檢查由服務層呼叫 `policy.js` 的 `canBook`，見 R-08）。
- **理由**：授權規則集中成一個沒有 I/O 的函式，才能用「角色 × 動作 × 資源」的表格測試窮舉（SC-007 要求跨權限操作 100% 被拒絕），也避免每個端點各自判斷而漏掉一處（NFR-012 要求略過畫面直接送出也要被拒絕）。
- **考慮過的替代方案**：在路由層用角色清單做閘門，無法表達「只能處理自己負責的場地」「不能審核自己的申請」這種依資料而定的規則。

## R-06 時間儲存與台北時間

- **對應需求**：FR-006、FR-011、FR-012、FR-013、FR-046、FR-077、NFR-014
- **決策**：
  1. 資料庫所有時間欄位使用 `DATETIME(3)` 存 UTC；連線池設定 `timezone: 'Z'`，並在每條連線執行 `SET time_zone = '+00:00'`。程式與 SQL 一律不使用 `NOW()`、`CURDATE()`，目前時間由 `backend/src/clock.js` 的 `now()` 取得，以參數 `:now` 帶入 SQL（理由見 R-17 的時鐘注入）。
  2. 台北時間運算集中在 `shared/src/taipei.js`：固定偏移 +8 小時（規格 NFR-014 已固定 UTC+8），提供「台北日期與時分拆解、由台北日期時間組回 UTC、台北星期幾、當日起點、加 n 個月（月底往前取）」。
  3. API 接受預約時間時，使用台北當地的 `date`（`YYYY-MM-DD`）、`startTime`、`endTime`（`HH:mm`）三個字串，由伺服器轉成 UTC；回應的時間欄位為 ISO 8601 的 UTC 字串。這樣使用者裝置的時區不會影響判斷。
  4. 場地開放時段存在 `venue_opening_hours`（`venue_id`、`weekday` 0 到 6、`open_minute`、`close_minute`，皆為台北當地一天內的分鐘數，30 的倍數）。一個星期幾可有多段。預約必須完整落在同一段內（FR-013）。
  5. 畫面、站內通知內容與 CSV 的時間，一律用 `Intl.DateTimeFormat('zh-TW', { timeZone: 'Asia/Taipei', hourCycle: 'h23' })` 格式化。「最遠 30 天」以台北日期計算（FR-012）。
- **理由**：規格要求不隨裝置時區改變（NFR-014）。伺服器端接收台北當地字串，避免瀏覽器把時間轉成 UTC 後在日期邊界（例如台北 00:30）出錯。固定偏移比引入時區資料庫簡單，且規格已固定為 UTC+8。
- **考慮過的替代方案**：資料庫存台北當地時間，會讓報表跨日與日後換時區都難處理。用 `NOW()` 計算會讓測試無法控制時間，也使排程邏輯與資料庫時鐘耦合。

## R-07 場地時段占用與併發

- **對應需求**：FR-014、FR-016、FR-018、FR-026、FR-028、FR-029、FR-030、FR-031、FR-032、FR-037、FR-040、FR-062、FR-067、FR-072、FR-082、NFR-003、NFR-007、NFR-008、SC-001
- **決策**：
  1. 以「30 分鐘時段列」讓資料庫保證不重疊：表 `booking_slots(venue_id, slot_start, holder_type, holder_id)`，`PRIMARY KEY (venue_id, slot_start)`，`slot_start` 為 UTC 的 `DATETIME(3)`，`holder_type` 取 `booking`、`hold`（候補保留，見 R-11）、`maintenance`（維護時段）。有效預約（待審核、已確認、已報到）、候補保留與維護時段各占用它涵蓋的每一個 30 分鐘列（單次最長 4 小時，即至多 8 列，規則上限放寬時按規則計）。
  2. 建立預約：先以純函式檢查 FR-011 到 FR-013（長度、單位、30 天、開放時段、人數），通過後在交易內先插入 `bookings`，再用單一多列 `INSERT` 依 `slot_start` 由小到大寫入時段列。主鍵衝突（錯誤碼 `ER_DUP_ENTRY`）時回滾並回 `409`「該時段已被占用」；兩人同時送出時，後插入的一方會等待先插入者的交易結果，先提交者成功、另一方得到重複鍵錯誤（SC-001）。遇到死結（`ER_LOCK_DEADLOCK`）或鎖逾時，以隨機 20 到 100 毫秒的間隔重試最多 3 次，仍失敗就回 `409` 並提示重試。
  3. 釋出時段：取消、駁回、自動取消、管理員取消都是刪除該預約的時段列。判定未到場時，刪除 `slot_start` 大於等於「判定時間之後的下一個整點或半點」的列，已過去的部分保留（例如 10:00 到 12:00 的預約於 10:15 判定，10:30 起釋出，FR-040）。已完成的預約其時段列保留到 R-10 的清理工作刪除。
  4. 修改時間或場地（FR-029、FR-030、NFR-003）：在同一個交易內先刪除這筆預約自己的時段列，再插入新時段列；新時段重複鍵時整個交易回滾，原時段列自動恢復，預約維持原狀。修改後的場地需要審核時，同一交易內呼叫 R-09 的 `transition` 把狀態改為 `pending`，不需審核時維持 `confirmed`（FR-037）。只修改主題或人數時只更新 `bookings` 欄位，不動時段列與狀態，人數仍須不超過容納人數（FR-028、FR-031）。
  5. 設定維護時段：在同一個交易內先取消管理員已確認的受影響預約（見 R-02 的兩段式確認），再插入 `maintenance` 時段列；任何一步失敗全部回滾。
  6. 隔離等級維持 MySQL 預設的 `REPEATABLE READ`；重疊判斷完全依賴主鍵，不依賴「先查再插」。
- **理由**：規格要求併發時也不得出現重疊的有效預約（NFR-008），且時間單位固定為 30 分鐘（FR-011），所以把每個時段攤成一列，用主鍵就能讓資料庫拒絕重複，任何程式路徑（包含之後新增的）都繞不過去。修改與維護都在單一交易內，滿足全有或全無。刪除而不是標記失效，使主鍵永遠只代表目前有效的占用。
- **已知限制**：單次預約的時段列數取決於「單次時長上限」規則（見 R-15），管理員調高上限會增加每筆預約的列數；規模上限 200 位員工與 20 個場地（NFR-007）下，資料量仍小。
- **考慮過的替代方案**：在場地列上用 `SELECT ... FOR UPDATE` 加鎖後再查詢區間重疊，也能正確，但正確性完全依賴每條程式路徑都記得加鎖，資料庫本身不擋重疊。MySQL 沒有時間範圍的排除約束，無法像某些其他資料庫那樣直接宣告「區間不得重疊」。`GET_LOCK` 是連線層級的鎖，不跟著交易回滾，連線池重用時容易漏放。

## R-08 持有額度與使用者層級的並行控制

- **對應需求**：FR-015、FR-042、FR-043、FR-044、FR-048、FR-049、FR-060、NFR-009
- **決策**：
  1. 凡是會增加「未來有效預約」或「週期性預約批數」的交易（建立預約、建立週期性預約、候補確認、修改後從已確認回到待審核不算新增），第一個鎖定的資源都是使用者列：`SELECT id, suspended_until FROM users WHERE id = :userId FOR UPDATE`。鎖順序固定為「使用者列、`bookings` 列、`booking_slots` 時段列（由小到大）」，所有交易遵守同一順序，避免死結。
  2. 鎖定後在同一交易內計算持有筆數：
     `SELECT COUNT(DISTINCT IF(series_id IS NULL, CONCAT('b', id), CONCAT('s', series_id))) FROM bookings WHERE user_id = :userId AND status IN ('pending', 'confirmed') AND start_at > :now`，一整批週期性預約只算 1 筆（FR-048）。批數另以 `COUNT(DISTINCT series_id)` 同樣條件計算，與上限比較（FR-049）。上限由規則表取得（見 R-15）。
  3. 暫停檢查也在鎖定後進行：`suspended_until > :now` 時回 `409`，訊息含解除時間（FR-043）。解除不需要排程工作，只要比較目前時間（FR-044）。
  4. 候補不計入持有筆數（FR-060），因為候補表與 `bookings` 是不同的表。
  5. 未到場累計與暫停（FR-042、FR-044）：R-10 把預約改為 `no_show` 的同一交易內，鎖使用者列後計算 `booking_events` 中該使用者 `to_status = 'no_show'`、`occurred_at` 晚於「目前時間減統計天數」且晚於 `users.no_show_counted_from` 的筆數；達到次數門檻時，把 `suspended_until` 設為目前時間加暫停天數，並把 `no_show_counted_from` 設為 `suspended_until`，所以暫停期間發生的未到場不會延長暫停，恢復後重新累計，並建立暫停通知（見 R-13）。
- **理由**：同一人併發送出多筆預約時，若只靠「先數再插」，兩個交易可能同時讀到 4 筆而各自新增，變成 6 筆（NFR-009）。鎖住使用者列讓同一人的這類操作排隊，不同人之間互不影響。
- **考慮過的替代方案**：在 `users` 上維護計數欄位，取消、過期、未到場等十多條路徑都要同步增減，漏一處就永久偏差；即時用 `COUNT` 查詢加使用者列鎖更不易出錯。

## R-09 預約狀態機與操作紀錄

- **對應需求**：FR-027、FR-034、FR-035、FR-036、FR-038、FR-039、FR-040、FR-041、FR-081、FR-082、FR-083、FR-084、NFR-010、SC-006、US7-7
- **決策**：
  1. 狀態以英文代碼存放：`pending`、`confirmed`、`checked_in`、`completed`、`rejected`、`cancelled`、`no_show`，中文名稱集中在 `shared/src/copy.js`。允許的轉換寫成 `backend/src/domain/bookingStateMachine.js` 中的一張表，與 FR-081 逐項對應，包含 `confirmed` 到 `pending`（FR-037 的修改）。
  2. 所有狀態變更都經過同一個服務函式 `transition(tx, bookingId, to, actor, reason, extra)`：先用 `UPDATE bookings SET status = :to ... WHERE id = :id AND status = :from` 條件更新，影響列數為 0 就 `409`「此申請已被處理」（同一申請由兩位審核者同時處理時，只有先送達者生效，FR-035）；成功後在同一交易寫入一筆 `booking_events`（`booking_id`、`actor_user_id`（系統處理時為空）、`actor_type` 取 `user`、`reviewer`、`admin`、`system`、`occurred_at`、`from_status`、`to_status`、`reason`），並依 R-07 釋出時段、依 R-13 建立通知。逾時取消以 `bookings.late_cancel` 布林欄位記錄（FR-027），管理員取消不設定它（FR-072）。
  3. `booking_events` 與規則變更紀錄（見 R-15）不可更動：各建立 `BEFORE UPDATE` 與 `BEFORE DELETE` 觸發器，內容為 `SIGNAL SQLSTATE '45000'`，訊息為「紀錄不可修改」（NFR-010）。
  4. 管理員查看預約與紀錄是唯讀查詢（FR-084），不提供任何修改紀錄的端點。
  5. 審核駁回必須帶非空白的原因，由 `transition` 對 `rejected` 的轉換檢查（FR-034）。報到的時間窗檢查是純函式 `canCheckIn(booking, now, rules)`：狀態須為 `confirmed`，且 `now` 在「開始時間減報到開放分鐘」到「開始時間加報到截止分鐘」之間（含兩端），否則回 `409` 並說明可報到的時間（FR-038、FR-039）；通過後才呼叫 `transition` 改為 `checked_in`。
- **理由**：集中成單一入口，才能保證「每次變更都留下紀錄」（FR-083、SC-006）：沒有其他程式碼會直接更新 `status`。條件更新把「兩人同時審核」的競爭交給資料庫，不需要額外鎖。觸發器讓「不可被任何使用者修改或刪除」在資料庫層成立，而不只是程式約定。
- **考慮過的替代方案**：事件溯源（以事件重建狀態）對這個規模過度複雜。只靠程式約定不更新紀錄表，無法防止之後新增的程式路徑或手動 SQL 修改。

## R-10 背景排程

- **對應需求**：FR-024、FR-036、FR-040、FR-041、FR-044、FR-056、FR-063、FR-066、NFR-011、SC-005
- **決策**：
  1. 後端行程啟動一個 `setInterval` 掃描，間隔 `SCAN_INTERVAL_MS`（預設 `30000`），以旗標避免上一輪未完成時重疊執行；每輪呼叫 `runDueJobs(now)`，`now` 由 R-06 的 `now()` 取得。
  2. 每一種到期工作都是「查詢到期列 加 逐筆處理」：在交易內 `SELECT id ... WHERE 到期條件 ORDER BY 到期時間 LIMIT 100 FOR UPDATE SKIP LOCKED`，每筆呼叫 R-09 的 `transition`，單筆失敗只記錄日誌並繼續。處理到沒有到期列為止。到期工作如下：
     - 待審核逾期：單次預約在 `start_at` 已到仍為 `pending` 時改為 `cancelled`，原因「未於開始前完成審核」；週期性預約批次以最早一個未取消場次的開始時間判斷，整批取消（FR-036、FR-056）。
     - 未到場：`confirmed` 且已過報到截止（`start_at` 加上報到截止分鐘與 `end_at` 兩者取較早者）時改為 `no_show`，記錄一次未到場並檢查是否達暫停門檻（FR-040、FR-042）。
     - 完成：`checked_in` 且 `end_at` 已到時改為 `completed`（FR-041）。
     - 候補保留逾時與候補失效：見 R-11（FR-063、FR-066）。
     - 開始前提醒：`confirmed`、`reminder_sent_at` 為空、已進入提醒時間窗，且 `confirmed_at` 不晚於「開始時間減提醒分鐘」的預約，發送提醒並寫入 `reminder_sent_at`（FR-024）。時間或場地修改後重新確認時，`confirmed_at` 更新、`reminder_sent_at` 清空。
     - 清理：刪除 `slot_start` 早於 1 天前的時段列。
  3. 所有判斷都以資料庫中的狀態與時間為準，不依賴記憶體計時器；行程重啟後的第一輪掃描會補做所有已到期工作。
  4. 暫停期滿不需要工作：以 `suspended_until` 與目前時間比較（見 R-08，FR-044）。
- **理由**：規格要求自動處理在時間點後 1 分鐘內完成（NFR-011、SC-005）；30 秒掃描一次，最壞延遲約 30 秒加上處理時間，留有餘裕。狀態導向的查詢天然冪等，行程重啟或掃描重複都不會重複處理。`SKIP LOCKED` 讓將來同時有兩個後端行程時不會互相等待或重複處理同一列。
- **已知限制**：本版本預設只跑一個後端行程。掃描失敗或資料庫短暫斷線時，下一輪會補做，但中斷期間的到期工作會延遲。
- **考慮過的替代方案**：為每筆預約建立 `setTimeout` 會在行程重啟時消失。`node-cron` 之類的套件只解決「定時觸發」，狀態導向的查詢仍要自己寫（見 R-03）。訊息佇列與獨立排程服務對 200 人規模過度複雜。

## R-11 候補保留與遞補

- **對應需求**：FR-043、FR-058、FR-059、FR-060、FR-061、FR-062、FR-063、FR-064、FR-065、FR-066、FR-071、NFR-009、US10
- **決策**：
  1. 候補存在 `waitlist_entries`（`user_id`、`venue_id`、`start_at`、`end_at`、`topic`、`headcount`、`created_at`、`status`、`offer_expires_at`），`status` 取 `waiting`、`offered`、`confirmed`、`expired`、`cancelled`。順位依 `(created_at, id)` 由小到大，只與完全相同的場地與起訖時間比較（FR-059）。登記時要求該時段目前至少有一個時段列被占用，且內容符合 FR-011、FR-012、FR-013（FR-058）；同一人同場地同起訖時間已有 `waiting` 或 `offered` 的候補時拒絕（FR-060）。
  2. 釋出掛勾 `offerFreedSlots(tx, venueId, range, now)`：R-07 每次刪除時段列後，在同一交易內呼叫。它找出與釋出範圍重疊、`waiting` 的候補，依順位逐一處理：該候補的所有時段列都已空出，且 `now` 早於 `start_at` 減候補截止門檻（預設 1 小時）時，才設為 `offered`、`offer_expires_at` 設為 `now` 加確認時限（預設 30 分鐘），並把這些時段以 `hold` 寫入時段列、建立通知（FR-061、FR-062）。距開始已在 1 小時內時不通知、不保留，時段直接對所有人開放（FR-064）。部分空出（例如候補 10:00 到 12:00 只釋出 10:00 到 11:00）不遞補，等剩餘時段也空出時掛勾會再被呼叫。對象為被暫停預約的使用者時，直接標為 `expired` 並改處理下一位。
  3. 確認遞補：鎖使用者列（見 R-08），檢查候補仍是 `offered` 且未逾時、持有額度與暫停狀態，通過後建立預約（狀態依場地是否需要審核，與一般預約相同，FR-016、FR-032），並把該候補的 `hold` 時段列原地改成 `booking`（`UPDATE booking_slots SET holder_type = 'booking', holder_id = :bookingId WHERE holder_type = 'hold' AND holder_id = :entryId`），保留期間時段從未對外釋出，因此不會被他人搶走（FR-062、FR-063）。額度或暫停檢查失敗，候補改為 `expired`、刪除 `hold` 時段列並再呼叫掛勾，由下一位接手。
  4. 保留逾時由 R-10 的掃描處理：`offered` 且 `offer_expires_at` 已到的候補改為 `expired`、刪除 `hold` 列、呼叫掛勾；若此時距開始已在 1 小時內，掛勾不再通知，時段開放所有人（FR-064）。
  5. 候補在其 `start_at` 到達時仍未成立，由掃描改為 `expired`（FR-066）。使用者取消候補時改為 `cancelled`，順位自然前移（FR-065）。
  6. 掃描每一輪另外對仍在 `waiting` 的候補重新跑一次掛勾，作為保險，確保任何路徑漏呼叫時最晚下一輪補上。
  7. 停用場地或帳號（R-02 的兩段式確認）在同一交易內把相關的 `waiting` 與 `offered` 候補改為 `expired`、刪除對應的 `hold` 時段列，並通知候補者（FR-071）。
- **理由**：保留時段以 `hold` 寫入同一張時段表，讓 R-07 的主鍵直接擋下第一順位以外的人預約（FR-062），不需要另一套「保留」邏輯。遞補確認把 `hold` 改成 `booking`，從保留到成立沒有任何空窗。掛勾在釋出的同一交易內執行，釋出與通知第一順位是原子的。
- **考慮過的替代方案**：保留期間不占用時段、確認時才搶：第一順位確認前時段可能被他人預約，違反 FR-062。只靠定時掃描遞補：第一順位要等到下一輪才收到通知，延遲不必要。

## R-12 週期性預約

- **對應需求**：FR-045、FR-046、FR-047、FR-048、FR-049、FR-050、FR-051、FR-052、FR-053、FR-054、FR-055、FR-056、FR-057、NFR-004、US9
- **決策**：
  1. 一批週期性預約是 `booking_series` 加多筆 `bookings`（`series_id`、`series_index`）；每個場次都是一筆完整的預約，可獨立取消、報到與判定未到場（FR-057）。
  2. 場次展開是純函式 `expandSeries(firstDate, frequencyWeeks, lastDate, startTime, endTime)`，間隔 7 或 14 天，日期以台北日期計算；最後一場不得晚於第一場加規則的月數（`addTaipeiMonths`，見 R-06，預設 3 個月，FR-046）。第一場需符合 FR-012，後續場次不受 30 天限制，每個場次都需符合 FR-011、FR-013 與 FR-014（FR-047）。
  3. 送出前檢查（FR-050）是預覽端點，不寫入：逐場次檢查開放時段、維護時段與時段列是否已被占用，回傳每個場次的結果與衝突原因。
  4. 正式送出（FR-051、FR-052）帶上使用者確認略過的衝突日期清單 `skipDates`。交易內依序處理：鎖使用者列並檢查額度（R-08，整批算 1 筆、批數上限）；對不在 `skipDates` 的場次，逐一嘗試以 R-07 的方式插入時段列；任何一個場次出現重複鍵，就蒐集成「新的衝突」，全部嘗試後只要有新的衝突，整個交易回滾、不建立任何場次，並回傳最新的衝突清單。InnoDB 的重複鍵錯誤只回滾該語句，交易可以繼續，所以能一次蒐集所有衝突；遇到死結則整個交易重試（R-07）。全部成功才寫入 `bookings` 與 `booking_events`（NFR-004）。沒有任何場次可建立時拒絕（FR-051）。
  5. 取消單一場次或「該場次及之後」（FR-053）：同一交易內對符合條件、開始時間尚未到的場次逐一呼叫 `transition`，每個場次各自判定逾時取消。
  6. 需要審核的場地以整批審核（FR-055）：批次有自己的 `status`；核准或駁回時對所有未取消場次逐一呼叫 `transition`；逾期自動取消見 R-10。批次待審核期間拒絕修改個別場次（FR-054）。
- **理由**：每個場次是普通預約，報到、未到場、取消、報表都不需要為週期性預約另寫一套。以「先蒐集衝突、再整批回滾」處理競爭，讓「檢查通過後有人搶先占用」的情形在伺服器端再次被攔下，且不會留下部分場次（NFR-004）。
- **考慮過的替代方案**：只存週期規則、查詢時動態展開：每個場次無法獨立取消、報到與記錄未到場。送出時遇到第一個衝突就回滾：使用者每次只看到一個衝突，要反覆嘗試。

## R-13 站內通知

- **對應需求**：FR-022、FR-023、FR-024、FR-025、NFR-007、NFR-013、SC-004、US5
- **決策**：
  1. 表 `notifications(id, user_id, type, message, booking_id, created_at, read_at)`。通知在產生事件的同一交易內寫入（由 R-09 的 `transition`、R-11 的掛勾、R-10 的提醒工作呼叫 `notify(tx, userId, type, params)`），所以事件成功與通知寫入同生同滅。`message` 在寫入當下用 `shared/src/copy.js` 的樣板組成，時間以台北時間格式化（R-06）。
  2. 查詢一律帶 `user_id` 為目前使用者，依 `(created_at, id)` 由新到舊排序，每頁 50 筆；提供未讀數與標記已讀的端點。開啟一則通知時把它的 `read_at` 設為目前時間（FR-025）。
  3. 前端以 `setInterval` 每 30 秒輪詢未讀數，頁面隱藏（`document.hidden`）時暫停，回到前景時立即查詢一次；不使用 WebSocket 與 Email。
- **理由**：規格只要求站內通知（FR-022、FR-023），產生通知的時間要求是事件後 1 分鐘內（SC-004），同一交易寫入保證不漏。輪詢對 200 人規模足夠，且省去維護長連線與多行程轉送（NFR-007）。
- **考慮過的替代方案**：WebSocket 或 Server-Sent Events 可以即時推送，但規格沒有即時顯示的需求，且要多處理斷線重連與行程間轉送。事件發生後非同步補寫通知，行程在兩者之間中斷時會漏通知。

## R-14 報表與 CSV 匯出

- **對應需求**：FR-077、FR-078、FR-079、FR-080、NFR-005、NFR-006、SC-008、US13
- **決策**：
  1. 報表計算寫成純函式 `backend/src/domain/report.js`，輸入是「區間內開始時間落在區間的預約列」與「場地的開放時段與維護時段」，輸出各場地的使用率、尖峰時段、取消率與未到場率。資料庫只負責取出預約列（一個場地一次查詢，選取狀態、起訖時間、是否逾時取消、取消操作者類型）。區間以台北日期含頭含尾，轉成 UTC 範圍查詢（R-06）。
  2. 使用率：分子是 `checked_in` 與 `completed` 預約的總分鐘數，分母是區間內開放時段扣除維護時段（取區間交集）的總分鐘數；分母為 0 時顯示「無資料」，分子為 0 且分母大於 0 時顯示 0%（FR-077、FR-080）。尖峰時段：把 `checked_in` 與 `completed` 預約依「台北星期幾加整點」累加占用分鐘，取前 3 名。取消率：分子是預約者本人取消的筆數，分母是狀態不是 `rejected` 的預約筆數，逾時取消另外列出筆數；管理員取消不計入分子也不計入分母（FR-072）。未到場率：分子是 `no_show` 筆數，分母是 `checked_in`、`completed`、`no_show` 的總筆數。
  3. 百分比四捨五入到小數點後 1 位，整數時不顯示小數點（例如 25% 與 33.3%）。
  4. CSV 由 `backend/src/domain/csv.js` 自寫序列化：UTF-8 並加位元組順序標記（BOM），換行用 CRLF，欄位含逗號、雙引號或換行時以雙引號包起來並將雙引號重複一次，開頭是 `=`、`+`、`-`、`@` 的儲存格前面加單引號，避免在試算表被當成公式。匯出端點回應 `Content-Type: text/csv; charset=utf-8` 與 `Content-Disposition: attachment`，欄位值使用與畫面相同的格式化函式，內容與畫面一致（FR-079、SC-008）。
  5. 報表的計算在應用程式內進行：一年區間、20 個場地的預約列數有限，查詢加計算須在 5 秒內完成（NFR-006）。
- **理由**：純函式可以直接用手算的例子測試（SC-008 要求與手動計算 100% 相同），分母需要「每週開放時段扣維護時段」的區間運算，用 SQL 表達既複雜又難測。BOM 讓 Excel 開啟繁體中文 CSV 不亂碼（NFR-005）。
- **已知限制**：應用程式內計算的記憶體用量與區間內的預約列數成正比；超過規格規模（NFR-007）的資料量需另行評估。
- **考慮過的替代方案**：用 SQL 聚合直接算使用率，分母的開放時段扣維護時段運算複雜且不易測試。CSV 套件在固定欄位的報表上沒有額外效益。

## R-15 規則管理

- **對應需求**：FR-073、FR-074、FR-075、FR-076、NFR-010、US12
- **決策**：
  1. 表 `rules(rule_key PRIMARY KEY, int_value, updated_at, updated_by)`，由遷移（見 R-18）寫入全部預設值；規則鍵與單位如下，時間類規則一律以「分鐘」儲存：

| 規則鍵                     | 單位 | 預設值 |
| -------------------------- | ---- | ------ |
| `max_duration_minutes`     | 分鐘 | 240    |
| `max_advance_days`         | 天   | 30     |
| `max_active_bookings`      | 筆   | 5      |
| `max_active_series`        | 批   | 2      |
| `max_series_months`        | 月   | 3      |
| `late_cancel_minutes`      | 分鐘 | 60     |
| `waitlist_confirm_minutes` | 分鐘 | 30     |
| `waitlist_cutoff_minutes`  | 分鐘 | 60     |
| `checkin_open_minutes`     | 分鐘 | 10     |
| `checkin_close_minutes`    | 分鐘 | 15     |
| `no_show_window_days`      | 天   | 30     |
| `no_show_threshold`        | 次   | 3      |
| `suspend_days`             | 天   | 7      |
| `reminder_minutes`         | 分鐘 | 30     |

2. 每個交易在開始時讀取一次完整規則表（約 14 列），整個交易使用同一份快照；不做跨請求快取，所以管理員修改後的下一個新操作立刻使用新值（FR-075）。已存在的預約不被改動：規則只在判定新操作與到期工作時讀取，不寫回預約列。
3. 修改時驗證每個值為正整數（FR-074）；因為時間單位固定為 30 分鐘，`max_duration_minutes` 還必須是 30 的倍數。每次修改在同一交易內寫入 `rule_changes`（操作者、時間、規則鍵、舊值、新值），該表同樣有 R-09 的不可更動觸發器（FR-076）。

- **理由**：規則以資料而非程式碼存在，管理員可在系統內調整（FR-073）；整個交易使用同一份快照，同一操作中途不會因規則被改而前後不一致。不快取讓「之後的新操作使用新值」不需要通知機制。
- **考慮過的替代方案**：環境變數需要重啟行程，管理員無法在系統內調整。記憶體快取加失效通知在單行程下可行，但每次請求多讀十幾列對 200 人規模的負擔可以忽略，不值得增加複雜度。

## R-16 前端架構

- **對應需求**：FR-019、FR-020、FR-021、FR-025、NFR-014、NFR-015、NFR-016、SC-003、SC-009、US3、US4、US7、US13
- **決策**：`vite@^8.0.0` 建置單一 `index.html`，前端執行期套件為 0。路由是 hash 路由，元件是回傳 DOM 節點的函式，另提供約 30 行的 `h(tag, props, ...children)` 小工具建立節點。開發時 Vite 把 `/api` 轉到 `http://localhost:3000`，正式環境由 R-02 的 HTTP 伺服器提供 `frontend/dist`。
  1. 路由：`#/login`、`#/change-password`、`#/venues`（搜尋與列表）、`#/venues/:id`（含日／週行事曆）、`#/bookings`（我的預約）、`#/waitlist`、`#/notifications`、`#/reviews`（待審核清單）、`#/admin/venues`、`#/admin/users`、`#/admin/rules`、`#/admin/reports`、`#/admin/bookings`。選單項目依 `GET` 目前使用者的角色顯示，但授權以伺服器為準（見 R-05）。
  2. 行事曆以 CSS Grid 繪製：一天為 30 分鐘一列，狀態以文字加顏色顯示（已預約、維護中、可預約、不開放）。週檢視在寬度 768 像素以上為七欄；低於 768 像素改為依日期由上而下堆疊的七個區塊，不使用水平捲動。寬度 360 像素時內容不得需要水平捲動（NFR-016）。
  3. 表單的時間以 `<input type="date">` 搭配 30 分鐘間隔的 `<select>` 選擇，只送出台北當地的日期與時分（見 R-06）；表格在窄螢幕以 CSS 改為卡片版面。
  4. 文案與錯誤訊息集中在 `shared/src/copy.js`（含預約狀態的中文名稱），前後端引用同一句；`<html lang="zh-Hant-TW">`。可點的控制項在呼叫 `fetch` 之前就設定 `disabled`，避免重複送出。
  5. 時間顯示與輸入範圍判斷使用 `shared/src/taipei.js`（見 R-06）。
- **理由**：頁面數量多，但每頁都是表單、列表或格狀行事曆，不需要複雜的前端狀態管理。hash 路由正式環境不需要伺服器做 fallback。沿用參考環境的做法讓套件只剩建置用的 Vite。行事曆在手機堆疊顯示，才能同時滿足桌機與手機（NFR-016、SC-009）。
- **前端執行期相依**：**0 個**。
- **考慮過的替代方案**：React 或 Vue 可減少手寫 DOM 更新，但與參考環境的原生做法不同，並且多出執行期與建置相依；本系統頁面多為由伺服器資料整頁重繪，手寫成本可接受。History API 路由需要伺服器對所有前端路徑回傳 `index.html`，hash 路由不必。

## R-17 測試策略

- **對應需求**：SC-001、SC-002、SC-005、SC-006、SC-007、SC-008、SC-009、SC-010、US3、US8
- **決策**：依下表分層。`shared` 與 `backend/src/domain` 的純函式由 `node:test` 直接載入。

| 層級           | 工具                                                                                                                                                         | 範圍                                                                                                                                                                                      |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 共用與領域單元 | `node:test`，`--experimental-test-coverage`，`--test-coverage-include` 指到 `shared/src/**/*.js` 與 `backend/src/domain/**/*.js`，`--test-coverage-lines=90` | 預約規則檢查、台北時間運算、狀態轉換表、授權矩陣、場次展開、報表計算、CSV 序列化                                                                                                          |
| 後端整合       | `node:test` 加內建 `fetch`，對本機 MySQL 資料庫 `venue_booking_test`                                                                                         | 時段占用、持有額度、候補保留、週期性預約的全有或全無、觸發器不可修改                                                                                                                      |
| 併發           | 同上，整合測試內並行送出                                                                                                                                     | 以測試輔助函式直接寫入階段（不經過 scrypt 登入），100 個使用者同時預約同一場地同一時段，確認恰好 1 筆成功、時段列與預約列各 1 組（SC-001）；同一人併發送出 6 筆預約確認持有筆數不超過上限 |
| 驗收（BDD）    | `@cucumber/cucumber@^13.0.0` 加 `playwright@^1.65.0`。`.feature` 第一行 `# language: zh-TW`，步驟用假設、當、那麼                                            | spec.md 的驗收情境；瀏覽器專案為 Playwright 附帶的 Chromium、Firefox、WebKit，另以 360×740 的行動視窗重跑一輪（SC-009）                                                                   |
| 效能           | `node:test` 加種子腳本                                                                                                                                       | 種子資料為 200 位員工、20 個場地、一年預約紀錄（約 2 萬筆）；量測查詢、行事曆、送出預約的 95 百分位須在 2 秒內，報表須在 5 秒內（SC-010、NFR-006），以 `npm run test:perf` 單獨執行       |

時鐘注入：領域函式與排程函式都接受 `now` 參數；後端的 `clock.js` 預設回傳系統時間，只有環境變數 `ENABLE_TEST_CLOCK=1`（僅在 BDD 啟動時設定）才開放 `PUT /__test/clock`（設定目前時間）與 `POST /__test/tick`（立即執行一輪 R-10 的掃描），未啟用時這兩個路徑回 `404`。BDD 用它驗證「開始前 30 分鐘提醒」「逾期未審核自動取消」「15 分鐘後判定未到場」「候補 30 分鐘逾時」，不真的等待。

- **理由**：驗收情境已是假設、當、那麼，Cucumber 的 `zh-TW` 方言直接使用這些關鍵字（SC-005、SC-006 的時間門檻靠時鐘注入驗證）。併發與持有額度是最容易在整合層才出錯的需求，必須有真實資料庫的測試。授權矩陣與報表是純函式，用表格窮舉（SC-007、SC-008）。
- **確定性**：每個整合測試使用獨立的 `venue_booking_test` 資料庫，開始前清空資料表；BDD 不連外網；時間一律由注入的時鐘提供，SQL 不使用 `NOW()`（見 R-06）。
- **已知限制**：Playwright 附帶的是 Chromium、Firefox 與 WebKit 引擎，不是每個品牌瀏覽器的安裝包；行動版以視窗大小模擬，不是實機。SC-003（90% 使用者 2 分鐘內完成預約）需要真人可用性測試，不納入自動化。
- **考慮過的替代方案**：Jest 與原生 ES Modules 的設定比 `node:test` 多。只用 Playwright Test 而不經過 Cucumber，驗收句子就不會跟 spec.md 的假設、當、那麼共用同一份 `.feature`。用 SQLite 跑整合測試，無法驗證 MySQL 的重複鍵、死結與 `SKIP LOCKED` 行為。

## R-18 設定、遷移與程式碼品質工具

- **對應需求**：FR-001、FR-073、NFR-010、NFR-016
- **決策**：
  - 環境變數使用 Node 內建的 `--env-file=.env`。至少包含 `PORT`、`DATABASE_URL`、`ALLOWED_ORIGINS`、`SCAN_INTERVAL_MS`、`ENABLE_TEST_CLOCK`（預設不設）。第一位管理員用 `ADMIN_BOOTSTRAP_EMAIL` 與 `ADMIN_BOOTSTRAP_PASSWORD` 提供，由指令 `npm run bootstrap-admin -w backend` 建立；系統已有管理員時指令不做事（FR-001 不提供註冊，需要有人建立第一個管理員）。
  - 資料庫遷移：`backend/src/db/migrations/*.sql`，依檔名順序執行，約 30 行的腳本以 `schema_migrations` 記錄已跑過的檔名，遷移連線才開啟 `multipleStatements`。遷移內容包含資料表、規則預設值（R-15）與不可更動觸發器（R-09）。不使用 ORM。連線池 `connectionLimit: 10`、`namedPlaceholders: true`、`timezone: 'Z'`。
  - 資料庫字元集 `utf8mb4`。
  - Lint 與格式化：`eslint@^10.0.0`（只使用 `eslint.config.js` 這種 flat config）與 `prettier@^3.9.0`，放在儲存庫根目錄。
  - npm workspaces：`frontend`、`backend`、`shared`、`e2e`。`shared` 沒有相依套件，放 `taipei.js`（台北時間運算，R-06）、`copy.js`（文案與狀態名稱）與前後端共用的預約規則常數。預約規則檢查函式放在 `backend/src/domain`，不進到瀏覽器。
- **理由**：`--env-file` 在 Node.js 24 已不是實驗旗標，不必再裝載入環境變數的套件。第一位管理員必須有帶外的建立方式，否則沒有註冊的系統無法啟用。遷移腳本把觸發器與預設規則一併版本化，新環境一次建好。`shared` 讓時間運算、狀態名稱與錯誤文句只有一份，前後端不會各寫一套。
- **考慮過的替代方案**：`dotenv` 與內建的 `--env-file` 重複。ORM 會為了二十張左右的表再加執行期套件，也會把遷移用的 SQL 與觸發器藏起來。
