# 資料模型分析規範

## Rule 1 -- 每個讀寫欄位必須有存放位置

**強度：MUST**

前置產出 `x-inner-needs.data` 列出的每個資料名稱與欄位，都必須對應到某張資料表的欄位；名稱或欄位調整時以欄位 note 說明對應關係。不得新增前置產出與介面列都沒有需要、也不是本檔關聯父表的資料表。

### Good Example

這個範例的 `has_thumbnail` 對應 API 讀取的同名欄位，並說明用途。

```dbml
  has_thumbnail tinyint [not null, default: 0, note: '1 表示已有縮圖檔']
```

### Bad Example

這個範例漏掉 API 要讀取的 `has_thumbnail`，後端只能每次查檔案系統判斷縮圖是否存在。

```dbml
Table photos {
  id char(36) [pk]
  content_hash char(64) [not null]
}
```

## Rule 2 -- 每個索引必須對應實際查詢

**強度：MUST**

每個索引與唯一鍵必須能指出它支援的 API 查詢、排序、分頁或去重需求，非一目了然時以索引 note 寫出。不得建立沒有查詢使用的索引，也不得漏掉分頁與唯一性需要的索引。

### Good Example

這個範例的複合索引寫出它支援相簿內游標分頁。

```dbml
    (album_id, taken_at, id) [name: 'ix_photos_album_taken', note: '供相簿內游標分頁']
```

### Bad Example

這個範例為每個欄位各建一個索引，沒有一個能支援依相簿與拍攝時間的游標分頁，寫入成本增加卻沒有改善查詢。

```dbml
    album_id
    taken_at
    created_at
```

## Rule 3 -- 多筆寫入必須寫出交易邊界

**強度：MUST**

一個 API 操作會寫入多筆資料或多張資料表、或必須全有或全無時，必須在 Project Note 的交易邊界表寫出交易範圍與失敗處理；與檔案寫入有先後關係時，必須寫出檔案在交易前或交易後處理。

### Good Example

這個範例寫出刪除照片的交易範圍，並說明檔案只在交易成功後刪除。

```markdown
| 刪除照片 | 刪除 photos 列；若該相簿已無照片則刪除 albums 列 | 整筆回滾，檔案刪除只在交易成功後執行 |
```

### Bad Example

這個範例只寫「使用交易」，看不出範圍與失敗處理，實作時可能先刪檔案再回滾資料，留下指向不存在檔案的資料列。

```markdown
| 刪除照片 | 使用交易 | 回滾 |
```

## Rule 4 -- 關聯的父表必須在本檔完整定義

**強度：MUST**

DBML 不支援跨檔引用，每個 `Ref` 的父表與父欄位都必須是本檔定義的 `Table` 與欄位。父表屬於先前功能時，必須讀取該功能的 `data-model.dbml`，在本檔完整寫出該表的欄位、索引與表 Note，不得只寫主鍵或以「詳見先前功能」代替；plan.md 或其他輸入文件寫明不重複定義先前功能的資料表時，仍依本規則寫出，並把該衝突列入回報。

### Good Example

這個範例的 photo_tags 參照先前功能的 photos，本檔完整寫出 photos 再建立關聯，parser 可以解析。

```dbml
Table photos {
  id char(36) [pk, note: '照片識別']
  album_id char(36) [not null, note: '所屬相簿']
  content_hash char(64) [not null, note: '檔案內容 SHA-256，用於去重']
  taken_at datetime [not null, note: '拍攝當地時間，無時區']
  date_estimated tinyint [not null, default: 0, note: '1 表示日期為推估']
  has_thumbnail tinyint [not null, default: 0, note: '1 表示已有縮圖檔']
  created_at datetime [not null, default: `CURRENT_TIMESTAMP`, note: '匯入完成時間']

  indexes {
    content_hash [unique, name: 'uk_photos_content_hash']
    (album_id, taken_at, id) [name: 'ix_photos_album_taken', note: '供相簿內游標分頁']
  }

  Note: '保存每一張已匯入照片的中繼資料；檔案本體不存放於此。'
}

Table photo_tags {
  photo_id char(36) [not null, note: '被標記的照片']
  tag varchar(32) [not null, note: '標籤文字']
}

Ref fk_photo_tags_photo_id: photo_tags.photo_id > photos.id [delete: cascade]
```

### Bad Example

這個範例依 plan.md「photos 不在本功能重複定義」只寫新表，Ref 指向本檔沒有的 photos，parser 回報找不到資料表，編輯器整份標紅、無法產生關聯圖。

```dbml
Table photo_tags {
  photo_id char(36) [not null, note: '被標記的照片']
  tag varchar(32) [not null, note: '標籤文字']
}

Ref fk_photo_tags_photo_id: photo_tags.photo_id > photos.id [delete: cascade]
```
