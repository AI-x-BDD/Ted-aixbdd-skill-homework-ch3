# 需求盤點規範

## Rule 1 -- 上線後才能量測的 SC 不列入覆蓋

**強度：MUST**

SC 的達成取決於系統行為，可以由程式或工具量測（如回應時間、分組正確率、無障礙檢測），就判定為需要建置並列入覆蓋。SC 的達成取決於使用者行為或營運結果（如首次使用成功率、滿意度、客服工單數），就判定為上線後才能量測，不列入覆蓋，並在報告的「不列入覆蓋的成功標準」寫出理由。

### Good Example

這個範例依達成條件是否取決於系統行為來區分，排除的 SC 附上理由。

```text
SC-003「開啟含 200 張照片的相簿時，第一屏縮圖在 1 秒內顯示」→ 需要建置（系統效能，可量測）
SC-005「90% 的使用者第一次使用就能完成匯入與瀏覽」→ 不列入覆蓋：易用性成果指標，上線後才能量測
```

### Bad Example

這個範例把易用性成果指標也列入覆蓋，SC-005 永遠找不到能實作它的任務，被誤報為覆蓋缺口，使用者會為它硬加一個無法完成的任務。

```text
SC-005「90% 的使用者第一次使用就能完成匯入與瀏覽」→ ❌ 沒有任務
```

## Rule 2 -- 只能由測試滿足的需求屬於範圍外

**強度：MUST**

需求的內容只要求驗證方式（如自動化驗收、測試覆蓋率、壓測），沒有要求系統行為時，必須判定為範圍外，覆蓋狀態標為 ➖，不列為覆蓋缺口，因為 tasks.md 依設計不含測試。需求同時要求系統行為與驗證方式時，系統行為的部分仍要列入覆蓋。

### Good Example

這個範例把只要求自動化驗證的 NFR-023 標為範圍外，同時要求效能與量測的 NFR-013 仍列入覆蓋。

```text
NFR-023「驗收情境與效能、容量 NFR 都必須能自動化驗證」→ ➖ 範圍外
NFR-013「匯入、開啟相簿、拖放排序的回應時間必須符合 SC-001、SC-003、SC-004」→ 列入覆蓋（系統效能）
```

### Bad Example

這個範例把 NFR-023 判為覆蓋缺口，報告會建議在 tasks.md 加入測試任務，違反 task skill 不含測試的設計。

```text
NFR-023 → ❌ 沒有任務，建議在 tasks.md 新增 e2e 測試任務
```

## Rule 3 -- 跨領域需求不要求對應介面

**強度：MUST**

不屬於特定畫面、API、資料表或儲存區的需求（如安全、相容性、可維護性、設定管理），必須判定為跨領域需求。跨領域需求沒有出現在 plan.md 介面盤點時，不得只因此列為發現事項，覆蓋改由 Setup、Foundational 或 Polish 任務判定。需求明確指向特定操作時（如某操作的回應時間），不屬於跨領域。

### Good Example

這個範例把設定管理的 NFR-018 判為跨領域，由 Foundational 任務判定覆蓋；指向特定操作的 NFR-014 不屬於跨領域，沒有介面依據它時才列為發現事項。

```text
NFR-018「儲存位置與連線設定必須可由環境變數調整」→ 跨領域，由 T005、T006、T012 覆蓋
NFR-014「所有點擊、按鍵、拖放 200ms 內要有可見回饋」→ 指向 UI 操作，介面盤點沒有介面依據它 → 列為發現事項
```

### Bad Example

這個範例把所有沒出現在介面盤點的 NFR 都列為覆蓋缺口，安全、相容性、可維護性的需求全部被誤報，使用者會為它們在 plan.md 硬加不存在的介面。

```text
NFR-017、NFR-018、NFR-019、NFR-021、NFR-022 → plan.md 介面盤點沒有對應介面，列為覆蓋缺口
```
