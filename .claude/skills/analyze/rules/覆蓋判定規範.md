# 覆蓋判定規範

## Rule 1 -- 覆蓋狀態依落點判定

**強度：MUST**

每個需求與介面的覆蓋狀態必須依下表判定，不得自訂其他狀態。

| 狀態      | 判定                                                                     |
| --------- | ------------------------------------------------------------------------ |
| ✅        | 需求的每個操作、條件與門檻都有任務實作                                   |
| ⚠️ 部分   | 有任務實作，但部分操作、條件或門檻沒有任務，或需要建置的量測工具沒有任務 |
| ❌        | 沒有任何任務實作                                                         |
| ➖ 範圍外 | 依需求盤點判定為範圍外                                                   |

### Good Example

這個範例中 NFR-014 要求所有點擊、按鍵、拖放都有回饋，但只有拖放有任務，判為部分覆蓋並寫出缺少的部分。

```text
NFR-014「所有點擊、按鍵、拖放 200ms 內要有可見回饋」→ T049（拖放）
狀態：⚠️ 部分 — 匯入、燈箱、刪除操作沒有任務要求即時回饋
```

### Bad Example

這個範例只要有一個任務就判為完整覆蓋，匯入、燈箱、刪除操作沒有回饋要求的缺口被隱藏，實作完成後才在驗收時被發現。

```text
NFR-014 → T049
狀態：✅
```

## Rule 2 -- 經介面連到的任務必須逐一確認

**強度：MUST**

追溯 JSON 的 `tasks_via_interface` 只是候選，同一個介面段落下的所有任務都會被列入。必須逐一確認任務描述確實實作了該需求，才能填入覆蓋表的任務欄；`tasks_direct` 也要確認不是只順帶提到需求編號。

### Good Example

這個範例從 18 個候選任務中，只保留確實實作相簿名稱的任務。

```text
FR-006「相簿名稱以拍攝日期顯示」
tasks_direct：T017；tasks_via_interface：T024～T029、T037～T046、T055～T057
確認後：T017（formatAlbumDate）、T032（卡片名稱）
```

### Bad Example

這個範例把候選任務全部填入，FR-006 看起來被 19 個任務覆蓋，真正缺漏的需求混在大量無關任務裡，覆蓋表失去判讀價值。

```text
FR-006 → T017、T024、T025、T026、T027、T028、T029、T037、T038、T039、T040、T041、T042、T044、T045、T046、T055、T056、T057
```

## Rule 3 -- 介面文檔覆蓋看主要段落的錨定

**強度：MUST**

介面的主要段落包括 Markdown 以介面 ID 開頭的段落、openapi.yaml 的 operation、data-model.dbml 的 Table、storage-contract.md 的儲存區段落，以及其他格式介面文檔的頂層定義（追溯 JSON 中 kind 為 `definition` 的段落，如 GraphQL 的 `type`、protobuf 的 `service`）。追溯 JSON 的 `unindexed_docs` 列出的文檔，必須讀原文找出其主要段落再逐一判定錨定。每個主要段落都至少被一個任務的必讀錨點直接指向時，介面才能判為 ✅。只錨定 schema 而沒有錨定 operation 時，該 operation 視為未錨定。operation、Table 與頂層定義依其描述與欄位對應到介面盤點的介面。

### Good Example

這個範例中 getAlbum 只透過 schema 被引用，判為未錨定，API-02 為部分覆蓋。

```text
API-02：listAlbums（T029）、getAlbum（無；T037 只錨定 components.schemas.PhotoDetail）、moveAlbum（T046）
狀態：⚠️ 部分 — getAlbum 沒有任務錨定
```

### Bad Example

這個範例把 schema 錨定視為 operation 已被錨定，實作 getAlbum 的任務讀不到該端點的 404 錯誤回應，實作時會漏掉錯誤處理。

```text
API-02：listAlbums、getAlbum、moveAlbum 都有相關任務
狀態：✅
```

## Rule 4 -- 基礎建設任務不列為反向覆蓋問題

**強度：MUST**

追溯 JSON 的 `tasks_without_requirement` 必須逐一判斷：Setup、Foundational、Polish 階段中建立專案結構、共用模組或收尾的任務，屬於支撐任務，只在報告中彙總說明，不列為發現事項。使用者故事階段中無法對應任何需求或介面的任務，必須列為覆蓋缺口。

### Good Example

這個範例把 Setup、Foundational 與 Polish 的任務彙總說明，不列為發現事項。

```text
未對應需求的任務：無。T001～T018 是 Setup 與 Foundational 基礎建設，T058 是 Polish 收尾，屬於合理的支撐任務。
```

### Bad Example

這個範例把 17 個基礎建設任務都列為「未對應需求」的發現事項，真正有問題的任務被淹沒，使用者也可能誤刪必要的基礎建設任務。

```text
C4：T001 沒有對應需求
C5：T002 沒有對應需求
C6：T003 沒有對應需求
```
