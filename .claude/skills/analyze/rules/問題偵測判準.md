# 問題偵測判準

## Rule 1 -- 模糊依訊號詞判定

**強度：MUST**

需求、驗收情境或任務描述含下列訊號，且同一句沒有可量測的門檻時，必須列為模糊：

| 類型       | 訊號                                                                                                       |
| ---------- | ---------------------------------------------------------------------------------------------------------- |
| 主觀形容詞 | 快速、迅速、即時、流暢、順暢、明顯、卡頓、延遲、友善、直覺、簡單、清楚、適當、合理、穩定、大量、良好、盡量 |
| 未定佔位   | TODO、TBD、待定、待補、待確認、???、`{{ }}`、`<placeholder>`                                               |

同一句已有數值門檻（如「200ms 內」「CLS ≤ 0.1」）時不算模糊。門檻只寫在 research.md、沒有寫在 spec.md 時，仍列為模糊，並在建議中指出門檻所在位置。

### Good Example

這個範例對有訊號詞且沒有門檻的句子列為模糊，並指出門檻只在 research.md；已有門檻的句子不列。

```text
SC-003「捲動時無明顯卡頓」→ 模糊：門檻 p95 200ms 只寫在 research.md R-14
NFR-014「200ms 內要有可見回饋」→ 不列（已有門檻）
```

### Bad Example

這個範例憑感覺判斷，把已有門檻的 NFR-014 列為模糊，SC-003 的「無明顯卡頓」反而沒列，有問題的句子沒找出，沒問題的句子又被誤報。

```text
NFR-014「200ms 內要有可見回饋」→ 模糊：「可見回饋」不夠具體
SC-003 → 不列
```

## Rule 2 -- 不重複偵測腳本負責的項目

**強度：MUST**

check_plan.py 與 check_tasks.py 已檢查的項目（介面 ID、需求引用、Wave 分配、統計數字、任務編號、相依引用、必讀錨點是否存在、殘留佔位符），不得再自行偵測。腳本回報的問題直接依回報內容列為發現事項，不另外判讀。

### Good Example

這個範例在 check_tasks.py 回報 0 個問題後，不再檢查錨點是否存在，只做腳本不涵蓋的錨點語意比對。

```text
check_tasks.py：0 個問題
→ 不再檢查錨點檔案與片段是否存在
→ 檢查 T037 實作 getAlbum，但必讀錨點只指向 schema（腳本不涵蓋）
```

### Bad Example

這個範例重新逐一比對每個錨點是否存在，結果與腳本相同卻多花大量 context，若比對方式和腳本不同，還會產生與腳本矛盾的結論。

```text
check_tasks.py：0 個問題
→ 逐一開啟 58 個任務的所有必讀錨點，確認檔案與片段存在
```

## Rule 3 -- 不一致必須列出雙方位置

**強度：MUST**

術語漂移、技術選型衝突、同一介面在 plan、介面文檔、tasks 之間描述不符，都屬於不一致。每個不一致的位置欄必須以「vs」列出衝突雙方的檔案與行號，摘要必須寫出雙方各自的說法。

### Good Example

這個範例以 vs 列出衝突雙方，摘要寫出雙方各自的 workspaces 內容。

```text
I1 | 不一致 | MEDIUM | tasks.md:L23（T001）vs plan.md:L23、techstack.md:L16 |
T001 的 workspaces 只有 ["frontend","backend"]，plan 與 techstack 是 frontend、backend、e2e
```

### Bad Example

這個範例只列出一方的位置，也沒寫出另一方的說法，使用者無法判斷該改 tasks.md 還是 plan.md。

```text
I1 | 不一致 | MEDIUM | tasks.md:L23 | T001 的 workspaces 設定不正確
```

## Rule 4 -- 內容一致的重述才算重複

**強度：MUST**

同一條規則在多處重述且內容完全一致時，才列為重複。重述的內容有出入時（如範圍、數值、用詞指向不同概念），必須列為不一致，不得列為重複。

### Good Example

這個範例把內容一致的重述列為重複，把用詞指向不同範圍的重述列為不一致。

```text
FR-018、邊界情況 L174、US4 情境 3 都寫「刪除最後一張照片時一併移除相簿」→ 重複
相簿定義「同一日期區間」vs FR-003「以天為單位」→ 不一致
```

### Bad Example

這個範例把範圍不同的兩句話列為重複並建議保留，「日期區間」與「以天為單位」的衝突沒有被修正，實作者可能依日期區間分組。

```text
D2 | 重複 | LOW | spec.md:L233、FR-003 | 相簿分組規則重述 | 可保留
```

## Rule 5 -- 照字面實作會出錯才算規格不足

**強度：MUST**

實作者照產物的字面實作會產生錯誤，或必須自行決定產物沒寫的關鍵資訊（如路徑基準、錯誤回應、狀態轉換）時，才列為規格不足。只是寫得不夠詳細、但不影響實作結果時，不列為規格不足。

### Good Example

這個範例指出照字面實作會解析出錯誤的路徑。

```text
U1：STORAGE_DIR 預設值 backend/storage 是相對路徑，start script 以 backend/ 為工作目錄執行，會解析成 backend/backend/storage
```

### Bad Example

這個範例把不影響實作結果的描述長短列為規格不足，真正會出錯的問題被淹沒在大量低價值的發現事項中。

```text
U3：T032 的卡片樣式描述只有一行，建議補充更多細節
```

## Rule 6 -- 憲法違反必須指出條款

**強度：MUST**

產物在所屬憲法條款的作用位置不符合條款要求時，列為憲法違反；SHOULD 條款已在產物寫出偏離理由時不列入。位置欄必須寫出產物的檔案與行號，並以「vs」接上條款編號；摘要必須寫出條款的要求與產物的實際內容。

### Good Example

這個範例寫出違反的條款編號，摘要對照條款要求與實際內容，使用者知道該回到 data-plan 補欄位。

```text
V1 | 憲法違反 | CRITICAL | data-model.dbml:L18-30（rooms）vs C-DATA-01 | 條款要求每張表有 created_at 與 updated_at，rooms 只有 created_at
```

### Bad Example

這個範例只寫「不符憲法」，沒有條款編號與實際內容，使用者無法判斷違反哪一條，也無從確認修正後是否符合。

```text
V1 | 憲法違反 | CRITICAL | data-model.dbml | 資料表不符憲法規定
```
