# 缺口影響力判準

## Rule 1 -- 只挑選會改變規格結果的缺口

**強度：MUST**

只有答案會改變使用者故事範圍、需求內容、資料定義、使用者可見行為或驗收結果的缺口，才能列為提問面向。答案不論為何都不影響上述任一項的缺口，不列入提問，在覆蓋總表標為 Outstanding。

### Good Example

這個範例挑選的缺口會改變需求與驗收結果，命名細節則不列入提問。

```markdown
提問面向：

- 主管請假時的代理審核：決定是否新增代理人角色與對應的驗收情境
  不列入（Outstanding）：
- 審核按鈕文字用「核准」或「同意」：不影響需求與驗收
```

### Bad Example

這個範例把按鈕文字列為提問面向，占用一題卻不改變任何需求，真正影響驗收的缺口可能因此排到下一輪。

```markdown
提問面向：

- 審核按鈕文字用「核准」或「同意」
- 主管請假時的代理審核
```

## Rule 2 -- 不得挑選技術與實作缺口

**強度：MUST**

缺口屬於技術選型、實作方式、資料儲存結構或任務拆解時，不得列為提問面向，在覆蓋總表標為 Deferred，並註明交由 technical-research、system-analysis 或 task 處理。只有缺少它時連使用者可見的行為都無法定義，才可改寫成使用者可見行為的問題後列入。

### Good Example

這個範例把資料庫選型標為 Deferred，並把「離線時能否送出」改寫成使用者可見行為的問題。

```markdown
提問面向：

- 網路中斷時員工能否先送出請假申請，恢復連線後再補送
  Deferred：
- 請假資料要存在 PostgreSQL 或 MongoDB → 交由 technical-research
```

### Bad Example

這個範例把資料庫選型列為提問面向，使用者在規格階段被迫做技術決策，也搶走了 technical-research 的職責。

```markdown
提問面向：

- 請假資料要存在 PostgreSQL 或 MongoDB
```

## Rule 3 -- 依影響乘以不確定性排序

**強度：MUST**

提問面向依「影響 × 不確定性」由高到低排序：影響看答案會改變的範圍大小（故事範圍 > 需求內容 > 單一驗收情境），不確定性看 spec.md 中可合理推得的解讀數量。同一分類有多個面向時，先排影響最大者；不得在高影響分類仍有缺口時，先排兩個以上低影響面向。

### Good Example

這個範例把影響整個故事範圍的代理審核排在第一，只影響單一情境的通知文案排在最後。

```markdown
1. 主管請假時的代理審核（影響故事範圍，可能解讀 3 種）
2. 特休餘額不足時能否預支（影響需求內容，可能解讀 2 種）
3. 審核結果通知的時間上限（影響單一驗收情境，可能解讀 2 種）
```

### Bad Example

這個範例依分類在表格中的順序排列，影響最大的代理審核排到最後，若使用者在第一輪後停止，最關鍵的缺口不會被問到。

```markdown
1. 審核結果通知的時間上限
2. 特休餘額不足時能否預支
3. 主管請假時的代理審核
```

## Rule 4 -- 推薦再問一輪必須有高影響缺口

**強度：MUST**

每輪結束後，只有剩餘缺口中仍有符合 Rule 1 且影響達「需求內容」以上的面向時，才可推薦再問一輪；否則推薦結束並進入下一步。推薦時必須列出這些面向與各自的影響，不得只寫「建議繼續」。

### Good Example

這個範例列出剩餘的高影響面向，讓使用者依具體內容決定是否繼續。

```markdown
剩餘高影響缺口：

- 特休餘額不足時能否預支（影響需求內容）
- 同一天重複送出請假時的處理（影響需求內容）
  推薦：再問一輪，上述兩項會改變 FR 與驗收情境。
```

### Bad Example

這個範例剩下的都是低影響缺口卻仍推薦繼續，也沒有列出理由，使用者被拖進一輪不會改變規格的訪談。

```markdown
推薦：建議再問一輪，讓規格更完整。
```
