# 釐清結果寫回規範

## Rule 1 -- 問答必須寫入當日場次

**強度：MUST**

本輪每個問答在「## 釐清紀錄」下寫成一行 `- [<覆蓋分類>] 問：<總結之提問> → 答：<使用者選擇與補充的合併結論>`，覆蓋分類為該題面向所屬的需求覆蓋分類名稱。已有今天日期的場次時接在該場次最後，否則在既有場次之後新增 `### 場次 YYYY-MM-DD`；spec.md 沒有「## 釐清紀錄」時，在「**狀態**」行之後、「**輸入**」行之前新增。以下 Example 皆對照此既有內容：

```markdown
**狀態**：草稿

## 釐清紀錄

### 場次 2026-10-25

- 問：第一版要涵蓋哪些假別？ → 答：特休與病假。

**輸入**：使用者描述：「幫我做一個請假申請功能」
```

### Good Example

這個範例在 2026-10-27 新增場次，接在既有場次之後，每行標出所屬覆蓋分類，答案寫成合併後的結論。

```markdown
### 場次 2026-10-25

- 問：第一版要涵蓋哪些假別？ → 答：特休與病假。

### 場次 2026-10-27

- [功能範圍與行為] 問：主管請假時，請假申請要由誰審核？ → 答：由主管事先指定的代理人審核；未指定代理人時改由上一層主管審核。

**輸入**：使用者描述：「幫我做一個請假申請功能」
```

### Bad Example

這個範例把問答併入舊場次，沒有標出覆蓋分類，也只記選項編號，日後看不出這題是哪一次訪談問的、補的是哪個覆蓋缺口，也看不出答案內容。

```markdown
### 場次 2026-10-25

- 問：第一版要涵蓋哪些假別？ → 答：特休與病假。
- 問：主管請假時，請假申請要由誰審核？ → 答：選項 1

**輸入**：使用者描述：「幫我做一個請假申請功能」
```

## Rule 2 -- 答案必須落入對應章節

**強度：MUST**

每個答案除了寫入釐清紀錄，還必須依下表改寫 spec.md 的對應章節；只寫入釐清紀錄而正文未改，視為未寫回。

| 答案性質               | 寫入章節                                         |
| ---------------------- | ------------------------------------------------ |
| 新增或縮減範圍、新角色 | 使用者故事（含驗收情境）                         |
| 系統行為               | 所屬故事或全域的功能需求                         |
| 品質要求               | 對應類別的非功能性需求，並把形容詞改為可量測條件 |
| 資料定義               | 關鍵實體                                         |
| 例外或失敗處理         | 邊界情況，必要時補驗收情境                       |
| 完成指標               | 成功標準                                         |
| 限制、取捨或不做的範圍 | 假設                                             |
| 用語統一               | 全文（依 Rule 4）                                |

### Good Example

這個範例把代理審核的答案同時寫進故事的驗收情境與功能需求。

```markdown
3. **假設** 主管已指定代理人且主管請假中，**當** 員工送出特休申請，**那麼** 申請送交代理人審核。

- **FR-009**：主管請假期間，系統**必須**將其待審申請改送主管指定的代理人；未指定代理人時改送上一層主管。
```

### Bad Example

這個範例只在釐清紀錄記下答案，功能需求與驗收情境沒有改，下游的 technical-research 與 task 讀正文時看不到代理審核。

```markdown
- [功能範圍與行為] 問：主管請假時，請假申請要由誰審核？ → 答：由主管事先指定的代理人審核。
```

## Rule 3 -- 被推翻的內容必須直接替換

**強度：MUST**

答案與 spec.md 既有內容衝突或使其失效時，必須直接改寫或刪除原內容，不得保留舊說法再另加新說法。「假設」中被本輪答案確認或推翻的 AI 預設值必須刪除，因為該決定已改由釐清紀錄記載。以下 Example 皆對照此既有內容：

```markdown
- **FR-012**：主管 3 天內未審核的申請，系統**必須**自動核准。

## 假設

- 主管逾期未審核時預設自動核准。
```

### Good Example

這個範例依答案改寫 FR-012，並刪除已被確認的假設。

```markdown
- **FR-012**：主管 3 個工作天內未審核的申請，系統**必須**改送上一層主管，不得自動核准。

## 假設
```

### Bad Example

這個範例保留舊需求並新增一條相反的需求，假設也未刪除，實作者面對兩條互相矛盾的 FR，無從判斷該做哪一個。

```markdown
- **FR-012**：主管 3 天內未審核的申請，系統**必須**自動核准。
- **FR-013**：主管 3 個工作天內未審核的申請，系統**必須**改送上一層主管。

## 假設

- 主管逾期未審核時預設自動核准。
```

## Rule 4 -- 同一概念全文只用一個詞

**強度：MUST**

答案確定某個概念的標準用語時，必須把 spec.md 全文的同義詞改為該用語，並在第一次出現處加註一次 `（原稱「<舊詞>」）`；之後不再出現舊詞。

### Good Example

這個範例統一使用「代理人」，只在第一次出現時加註舊詞。

```markdown
- **FR-009**：主管請假期間，系統**必須**將其待審申請改送代理人（原稱「代簽人」）。
- **FR-010**：代理人**必須**能在待審清單中看到代理的申請。
```

### Bad Example

這個範例新需求用「代理人」，舊需求仍寫「代簽人」，下游會把兩者當成不同角色，各自設計權限與畫面。

```markdown
- **FR-009**：主管請假期間，系統**必須**將其待審申請改送代理人。
- **FR-010**：代簽人**必須**能在待審清單中看到代理的申請。
```

## Rule 5 -- 新增項目後必須重新編號

**強度：MUST**

新增或刪除 FR、NFR、SC 或使用者故事後，必須依出現順序把同類編號重新從 1 連續編排，並同步更新全文引用這些編號之處。不得以跳號、`FR-009a` 或附加在章節末尾的方式迴避重新編號。

### Good Example

這個範例在故事 2 新增需求後，把原 FR-009 之後的編號往後推一號，並更新引用。

```markdown
- **FR-009**：主管請假期間，系統**必須**將其待審申請改送代理人。
- **FR-010**：系統**必須**在申請核准後通知員工（原 FR-009）。

- 代理人審核的通知方式同 FR-010。
```

### Bad Example

這個範例以 `FR-009a` 插入新需求，編號不再連續，check_spec.py 會回報編號錯誤，下游以編號引用需求時也容易遺漏。

```markdown
- **FR-009**：系統**必須**在申請核准後通知員工。
- **FR-009a**：主管請假期間，系統**必須**將其待審申請改送代理人。
```
