# 必讀錨點規範

## Rule 1 -- 每個任務的必讀必須自給自足

**強度：MUST**

每個任務完成時需要對照的所有位置，都必須列在該任務自己的必讀中，讓任務單獨拿出來執行也有完整參考。不得在 Phase 或端點段首寫「載入」等段落層級的參考，不得在檔頭列出前置文件清單，也不得以「同上」「見前一任務」省略；多個任務需要同一位置時各自列出。

### Good Example

這個範例的路由任務自己列出需要的契約與套件，不依賴段首或前一任務。

```markdown
- [ ] T039 [US1] 實作 `backend/src/routes/photos.js` 的 `POST /api/photos`：…
  - 📎 必讀：`contracts/openapi.yaml › importPhoto › requestBody` — multipart 欄位名稱、必填與順序以此為準
  - 📎 必讀：`techstack.md › 後端 › 上傳解析` — multipart 串流解析套件以此為準
```

### Bad Example

這個範例把參考放在端點段首，任務被單獨委派給 sub-agent 或上下文被摘要後，段首不會跟著任務走，執行的 AI 看不到契約。

```markdown
### 後端（API-01、API-02 列表）

**載入**：`techstack.md › 後端`、`contracts/openapi.yaml › importPhoto`

- [ ] T039 [US1] 實作 `backend/src/routes/photos.js` 的 `POST /api/photos`：…
```

## Rule 2 -- 錨點必須定位到段落或識別碼

**強度：MUST**

錨點固定寫成 `檔案 › 段落 › 識別碼`，檔案路徑相對於功能目錄，之後每段以 `›` 往下定位，同一層的多個對象以「、」並列。錨點必須至少定位到下表的層級，不得只寫檔名。

| 文件                          | 定位方式                                                                                                                                                                                   |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `contracts/openapi.yaml`      | `operationId`，可再接 `parameters`、`requestBody`、`responses` 與狀態碼；schema 寫 `components.schemas.<名稱>`                                                                             |
| `data-model.dbml`             | `Table <名稱>`，可再接欄位、索引名稱或 `Note`；外鍵寫 `Ref <名稱>`；交易寫 `Project Note › 交易邊界 › <交易列>`                                                                            |
| Markdown 契約、`techstack.md` | 標題文字，可再接表格的列名                                                                                                                                                                 |
| `spec.md`                     | `FR-`、`NFR-`、`SC-` 編號，或 `使用者故事 N › 驗收情境 M～K`、`邊界情況`                                                                                                                   |
| `research.md`                 | `R-` 編號                                                                                                                                                                                  |
| `contracts/prototype/*.html`  | `data-testid`                                                                                                                                                                              |
| 其他格式的介面文檔            | 該格式的頂層定義，寫成「關鍵字 名稱」（如 GraphQL 的 `type Room`、protobuf 的 `service RoomService`、`message JoinRequest`），可再接欄位或成員；沒有頂層定義的格式寫原文中的鍵路徑或識別碼 |

### Good Example

這個範例分別定位到 operation 的回應與 schema，執行的 AI 不需要讀整份契約。

```markdown
- 📎 必讀：`contracts/openapi.yaml › importPhoto › requestBody、responses 201／200／400／413／415／422` — 每個狀態碼的觸發條件與 multipart 欄位以此為準
- 📎 必讀：`contracts/openapi.yaml › components.schemas.ImportCreated` — 201 回應的必填欄位與型別以此為準
```

### Bad Example

這個範例只寫檔名，執行的 AI 要自行在數百行的契約中找相關部位，可能只看到第一個 operation 就開始實作。

```markdown
- 📎 必讀：`contracts/openapi.yaml` — API 規格以此為準
```

## Rule 3 -- Setup 任務必須綁 techstack.md 的具體列

**強度：MUST**

Setup Phase 的每個任務都必須至少有一條指向 techstack.md 具體段落或表格列的必讀，例如 `techstack.md › 套件安裝清單 › backend`、`techstack.md › 開發工具`。

### Good Example

這個範例把 frontend 設定檔任務綁到套件安裝清單中 frontend 的列。

```markdown
- [ ] T003 [P] 建立 `frontend/package.json`…
  - 📎 必讀：`techstack.md › 套件安裝清單 › frontend` — frontend 的 devDependencies 與版本以此為準
```

### Bad Example

這個範例的 Setup 任務沒有綁 techstack.md，執行的 AI 依記憶填入版本，與研究決定的版本不一致。

```markdown
- [ ] T003 [P] 建立 `frontend/package.json`…
  - 📎 必讀：`plan.md › 專案結構` — 目錄結構以此為準
```

## Rule 4 -- 需讀原因寫出以此為準的對象

**強度：MUST**

每條必讀在錨點後以「 — 」接一句需讀原因，寫出這個位置是哪些決定或內容的依據，或讀它要確認什麼，通常以「…以此為準」作結。不得轉述該位置的內容本身，例如列出欄位值、狀態碼意義或文案原文。

### Good Example

這個範例只說明以此為準的對象，欄位的實際值仍要讀原文。

```markdown
- 📎 必讀：`data-model.dbml › Table albums` — albums 的欄位、型別、預設值與索引以此為準
```

### Bad Example

這個範例在原因中轉述欄位內容，資料模型之後修改時這段轉述不會同步，執行的 AI 會照過時的轉述實作。

```markdown
- 📎 必讀：`data-model.dbml › Table albums` — id char(36)、album_date date、position int NULL
```
