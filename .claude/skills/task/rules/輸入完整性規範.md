# 輸入完整性規範

## Rule 1 -- 介面文檔依 Planner 的產出路徑判定

**強度：MUST**

每個端點應有的介面文檔，必須取該端點在 plan.md 介面盤點的介面 ID 前綴，依 [Planner 配對規範](../../planner-provisioning/rules/Planner配對規範.md) 找到對應的 Planner，再以該 Planner SKILL.md 中 `WRITE` 步驟寫明的檔案路徑判定。不得依檔案內容是否出現介面 ID、或依檔名猜測判定。

### Good Example

這個範例依前綴找到 Planner，再依 Planner 寫明的產出路徑逐一確認檔案。

```markdown
| 端點       | 介面前綴 | Planner        | 應有的介面文檔                                     | 狀態 |
| ---------- | -------- | -------------- | -------------------------------------------------- | ---- |
| 前端       | `UI`     | `ui-ux-plan`   | `contracts/ui-contract.md`、`contracts/prototype/` | 存在 |
| 後端       | `API`    | `api-plan`     | `contracts/openapi.yaml`                           | 存在 |
| 資料庫端   | `DB`     | `data-plan`    | `data-model.dbml`                                  | 存在 |
| 檔案系統端 | `FS`     | `storage-plan` | `contracts/storage-contract.md`                    | 存在 |
```

### Bad Example

這個範例以檔案內容是否出現介面 ID 判定，`openapi.yaml` 只出現 `UI-01`～`UI-04` 而被當成前端文檔，`storage-contract.md` 沒有出現 `FS-01` 而被判為缺少，結果誤擋了完整的輸入。

```markdown
UI：ui-contract.md、openapi.yaml、states.html
API：（找不到含 API-01 的檔案）→ 缺少
FS：（找不到含 FS-01 的檔案）→ 缺少
```

## Rule 2 -- 缺少任一介面文檔即停止

**強度：MUST**

有任一端點缺少應有的介面文檔時，必須停止，不得只為文檔齊全的端點產出部分任務，也不得把必讀改指向 plan.md 或 spec.md 來替代。停止時必須逐列寫出端點、介面前綴、Planner 與缺少的路徑。

### Good Example

這個範例在檔案系統端缺少文檔時停止，並列出補齊所需的資訊。

```markdown
| 端點       | 介面前綴 | Planner        | 缺少的介面文檔                  |
| ---------- | -------- | -------------- | ------------------------------- |
| 檔案系統端 | `FS`     | `storage-plan` | `contracts/storage-contract.md` |

請先執行 system-analysis 的分析 Wave 補齊上述文檔，再重新拆解任務。
```

### Bad Example

這個範例在缺少儲存契約時仍產出任務，檔案系統端任務的必讀改指 plan.md 介面盤點，執行時 AI 只能自行決定目錄結構與命名規則，與之後補上的契約互相衝突。

```markdown
### 檔案系統端（FS-01、FS-02）

- [ ] T027 [US1] 實作 `backend/src/services/fileStore.js`
  - 📎 必讀：`plan.md › 介面盤點 › FS-01` — 原始檔儲存區的範圍以此為準
```
