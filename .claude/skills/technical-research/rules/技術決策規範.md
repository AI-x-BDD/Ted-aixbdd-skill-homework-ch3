# 技術決策規範

## Rule 1 -- 決策不得違反使用者指定的限制

**強度：MUST**

決策必須遵守使用者指定的技術方向與限制（如「不使用框架」、「不使用第三方服務」、「套件越少越好」）。限制內找不到可行做法時，不得自行放寬限制。

### Good Example

這個範例在「不使用第三方服務」的限制下，把照片存在後端本機目錄，並在替代方案寫明雲端儲存因違反限制而不採用。

```markdown
- **決策**：照片原始檔與縮圖以檔案形式存放在後端的 `storage/` 目錄。
- **考慮過的替代方案**：雲端物件儲存則違反「不要第三方系統」。
```

### Bad Example

這個範例在同樣的限制下選用雲端圖片服務，違反使用者已拍板的限制，整份研究紀錄必須重做。

```markdown
- **決策**：照片上傳至 Cloudinary，由其產生縮圖與 CDN 網址。
```

## Rule 2 -- 決策必須具體到可直接實作

**強度：MUST**

決策必須寫出版本、套件名稱、關鍵參數或演算法等實作者不需再選擇的細節，不得只寫方向或類別。引入的每個套件都必須以 `` `套件名@版本範圍` `` 寫明版本範圍；套件名使用該套件管理工具安裝時的完整識別（如 npm 的 `@scope/name`、Go 的 module 路徑、Maven 的 `groupId:artifactId`），版本範圍使用該工具的原生語法（如 `^1.6.0`、`v1.5.3`、`>=2.31,<3`、`[2.0,3.0)`）。

### Good Example

這個範例以 `套件名@版本範圍` 寫出套件與版本，並寫出關鍵參數與失敗時的處理，實作者可直接動手。

```markdown
- **決策**：後端以 `busboy@^1.6.0` 串流解析 `multipart/form-data`，單檔上限 50 MB，超過時回應 `413`。
```

### Bad Example

這個範例只寫出套件名稱、沒有版本範圍，也沒有寫上限與錯誤處理，實作者安裝到不同主版號或自訂上限，產出不一致，techstack.md 也無版本可彙整。

```markdown
- **決策**：後端使用 `busboy` 解析上傳檔案。
```

## Rule 3 -- 理由必須連結到具體能力與需求

**強度：MUST**

理由必須寫出所選技術的具體能力或特性，以及它滿足的需求、成功標準或限制。不得只以「業界常用」、「效能較好」、「比較成熟」等無法查證的說法作為理由。

### Good Example

這個範例寫出唯一索引的具體作用，並連結到需求的判定標準與並行上傳情境。

```markdown
- **理由**：「檔案內容完全相同才算重複」正好對應內容雜湊；由資料庫唯一索引擋下重複，並行上傳也不會有競態問題。
```

### Bad Example

這個範例的理由空泛，看不出選擇與需求的關係，日後條件改變時無法判斷決策是否仍成立。

```markdown
- **理由**：SHA-256 是業界常用的做法，安全又可靠。
```

## Rule 4 -- 替代方案只列實際可行的方案

**強度：MUST**

「考慮過的替代方案」只列在目前限制下真的可以選用、或是常見但被限制排除的方案，並寫出不採用的具體原因。沒有可比較的方案時省略此欄，不得為了填欄位而編造明顯不合理的方案。

### Good Example

這個範例列出兩個實際可行的 HTTP 框架，各自寫出不採用的原因。

```markdown
- **考慮過的替代方案**：Express 生態成熟，但只為路由多引入一個相依套件，效益不高；Fastify 功能強大，但對本專案而言過度。
```

### Bad Example

這個範例編造沒有人會採用的方案，看似完成了比較，實際上沒有提供任何取捨資訊。

```markdown
- **考慮過的替代方案**：自行以組合語言實作 HTTP 伺服器，開發成本過高，因此不採用。
```

## Rule 5 -- 不確定的技術事實必須先查證

**強度：MUST**

作為決策或理由依據的技術事實（如某版本是否內建某功能、套件是否支援某格式、瀏覽器支援度）沒有把握時，必須先查閱官方文件或版本說明再寫入；無法查證的事實不得作為理由，必要時寫入「已知限制」並標明待驗證。

### Good Example

這個範例在寫入「sharp 不支援 HEIC」前查證了 sharp 官方文件，確認預設建置不含 HEVC 解碼，才作為不採用的理由。

```markdown
- **考慮過的替代方案**：`sharp` 含原生二進位檔，且預設建置不支援 HEVC 編碼的 HEIC 解碼，因此改由前端產生縮圖。
```

### Bad Example

這個範例憑印象斷言 Node 20 內建某參數，事實錯誤時實作階段才會發現，連帶推翻依此做出的測試策略。

```markdown
- **理由**：Node 20 已內建 `--test-coverage-lines`，不需要額外套件。
```
