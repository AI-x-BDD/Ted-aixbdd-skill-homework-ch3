# 執行順序規範

## Rule 1 -- 取可執行清單中檔案順序最前的範圍內任務

**強度：MUST**

下一個任務必須是腳本 `ready` 清單中、屬於範圍內、編號最小的任務。不得依個人判斷跳到後面的任務，也不得因任務標了 `[P]` 而同時執行多個任務或委派 sub-agent 並行；`[P]` 只表示順序可以調換，由同一個 agent 依編號逐一執行。

### Good Example

這個範例在 T002～T006 都可執行時取編號最小的 T002，逐一執行。

```text
ready：T002、T003、T004、T005、T006 → 執行 T002
```

### Bad Example

這個範例看到 T002～T006 都標 `[P]`，委派五個 sub-agent 同時執行，T004 與 T005 都在根目錄寫設定檔，彼此看不到對方的修改，ESLint 設定沒有涵蓋 vite.config.js。

```text
ready：T002～T006 皆為 [P] → 委派 5 個 sub-agent 並行
```

## Rule 2 -- 範圍內仍有未完成任務卻無可執行任務時停止

**強度：MUST**

腳本的 `remaining` 中仍有範圍內任務，但 `ready` 中沒有任何範圍內任務時，必須停止並列出這些任務的 `unmet_dependencies` 與 `unfinished_earlier_phase_tasks`。不得自行忽略相依或 Phase 閘門以繼續執行。

### Good Example

這個範例在 T026 依賴的 T018 未完成時停止並說明原因。

```text
範圍內剩餘 T026、T027，但都無法執行：
- T026 未滿足相依：T018
- T027 未滿足相依：T026
```

### Bad Example

這個範例判斷 T018 只是 API client，先寫 T026 再回頭補，roomPage.js 自行寫了一份 fetch 包裝，與 T018 的 client 重複且錯誤處理不一致。

```text
T018 尚未完成，但 T026 只需要呼叫 API，先直接用 fetch 實作。
```

## Rule 3 -- 故事 Checkpoint 不停下等待確認

**強度：MUST**

使用者故事 Phase 的任務全部完成後，直接繼續下一個 Phase，不得在 Checkpoint 停下詢問使用者是否繼續。只有遇到 SOP 中的停止條件時才停止。

### Good Example

這個範例完成 US1 最後一個任務後直接開始 US2。

```text
T027 完成（US1 Checkpoint）→ 繼續 T028
```

### Bad Example

這個範例在 US1 Checkpoint 停下詢問，使用者已選擇一次執行到底，每個故事都要再回覆一次才會繼續。

```text
US1 已完成，是否繼續 US2？(yes/no)
```
