# 儲存分析規範

## Rule 1 -- 每個讀寫的儲存區必須有一節

**強度：MUST**

前置產出 `x-inner-needs.files` 列出的每個儲存區都必須在契約中有一節，並涵蓋所有出現過的存取方式（read、write、delete）；介面列有、前置產出沒有讀寫的儲存區，也必須寫出用途。不得新增沒有任何需要的儲存區。

### Good Example

這個範例的縮圖儲存區有獨立一節，涵蓋 API 的寫入、讀取與刪除。

```markdown
## 縮圖儲存區

保存前端上傳的 JPEG 縮圖；沒有縮圖的照片不建立檔案。
```

### Bad Example

這個範例把縮圖併在原始檔一節的一句話，命名規則與刪除連動都沒有寫出，實作時縮圖可能與原始檔同名而互相覆蓋。

```markdown
## 原始檔儲存區

保存照片副本，縮圖也放在這裡。
```

## Rule 2 -- 必須寫出檔案與資料寫入的先後順序

**強度：MUST**

新增與刪除連動必須寫出檔案操作與資料列寫入的先後順序，以及其中一方失敗時另一方如何處理，順序必須與資料模型的交易邊界一致。

### Good Example

這個範例寫出正式路徑出現後才寫入資料列，失敗時刪除暫存檔。

```markdown
| 新增 | 串流寫入 `tmp/<upload_id>.part`；收完後原子改名到正式路徑。正式路徑出現後才寫入資料列。 |
| 新增失敗 | 刪除對應 `.part`；不得留下正式路徑的半寫入檔。 |
```

### Bad Example

這個範例沒有寫先後順序，實作時可能先寫資料列再寫檔案，中斷後資料列指向不存在的檔案。

```markdown
| 新增 | 儲存檔案並寫入資料庫。 |
```

## Rule 3 -- 必須涵蓋中斷與重複的處理

**強度：MUST**

每個可寫入的儲存區必須寫出新增失敗、啟動清理與重複內容三種時機的處理，讓中斷後不留下殘缺或孤兒檔案；儲存區沒有該時機時寫出不適用的原因。

### Good Example

這個範例寫出啟動時清除殘留暫存檔與沒有資料列的孤兒檔案。

```markdown
| 啟動清理 | 清除 `tmp/` 內殘留 `.part`，以及 `originals/` 中沒有對應資料列的檔案。 |
```

### Bad Example

這個範例只寫新增與刪除，斷電後殘留的暫存檔永遠不會被清除，儲存空間持續增加。

```markdown
| 新增 | 寫入正式路徑。 |
| 刪除照片 | 刪除正式檔。 |
```
