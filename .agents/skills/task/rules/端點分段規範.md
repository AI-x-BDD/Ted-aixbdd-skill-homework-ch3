# 端點分段規範

## Rule 1 -- 端點與介面範圍取自 plan.md 介面盤點

**強度：MUST**

使用者故事 Phase 內每個 h3 的端點名稱必須與 plan.md 介面盤點的「所屬端點」完全相同，括號內寫本故事涉及的介面 ID，同一介面只涉及部分功能時可加上簡短範圍（如「列表」「刪除」）。不得自創「共用」「整合」等盤點以外的端點，也不得把程式分層當成端點。

### Good Example

這個範例的端點名稱與 plan.md 相同，並以範圍標示只涉及 API-02 的列表。

```markdown
### 後端（API-01、API-02 列表）
```

### Bad Example

這個範例把後端的程式分層各開一節，plan.md 沒有這些端點，任務與介面文檔對不上，也無法從端點推得要讀哪份契約。

```markdown
### 路由層（albums、photos）

### 服務層（importService）
```

## Rule 2 -- 端點依實作相依由內而外排列

**強度：MUST**

h3 端點必須依實作相依排列，被呼叫的端點在前、呼叫它的端點在後，即 plan.md 分析 Wave 的反向順序；同一個 Wave 的端點維持 plan.md 中的先後。

### Good Example

這個範例的 plan.md Wave 為前端 → 後端 → 資料庫端、檔案系統端，任務依反向排列。

```markdown
### 資料庫端（DB-01、DB-02）

### 檔案系統端（FS-01、FS-02）

### 後端（API-01、API-02 列表）

### 前端（UI-01 瀏覽、UI-02）
```

### Bad Example

這個範例照 Wave 順序把前端排在最前面，前端任務完成時還沒有可呼叫的 API，相依只能指向後面的任務。

```markdown
### 前端（UI-01 瀏覽、UI-02）

### 後端（API-01、API-02 列表）

### 資料庫端（DB-01、DB-02）
```

## Rule 3 -- 任務依程式碼實作的介面歸屬端點

**強度：MUST**

任務歸屬它的程式碼直接實作或存取的介面所屬的端點：資料表的存取歸資料庫端，儲存區的讀寫歸檔案系統端，API 的路由、服務與共用邏輯歸後端，畫面與元件歸前端。跨端點協調的服務歸發起協調的端點。「路徑慣例」必須寫出每個端點的任務落在哪些目錄，與實際歸屬一致。

### Good Example

這個範例把 repository 歸資料庫端、fileStore 歸檔案系統端，協調兩者的匯入服務歸後端。

```markdown
### 資料庫端（DB-01、DB-02）

- [ ] T025 [P] [US1] 實作 `backend/src/repositories/albumRepository.js`：…

### 檔案系統端（FS-01、FS-02）

- [ ] T028 [US1] 實作 `backend/src/services/fileStore.js`：…

### 後端（API-01、API-02 列表）

- [ ] T033 [US1] 實作 `backend/src/services/importService.js`：…
```

### Bad Example

這個範例因檔案位於 `backend/` 就全部歸到後端，資料庫端與檔案系統端各只剩一個空殼，資料表與儲存契約的必讀散落在後端任務中難以對照。

```markdown
### 後端（API-01、API-02 列表）

- [ ] T025 [P] [US1] 實作 `backend/src/repositories/albumRepository.js`：…
- [ ] T028 [US1] 實作 `backend/src/services/fileStore.js`：…
```

## Rule 4 -- 未涉及的端點不列出

**強度：MUST**

使用者故事沒有任何任務的端點不得列出 h3，不得保留空節或寫「無」。

### Good Example

這個範例的 US2 沿用 US1 已完成的檔案讀取，沒有檔案系統端任務，因此不列該節。

```markdown
### 資料庫端（DB-01、DB-02 讀取）

### 後端（API-02 單本、API-03 讀取）

### 前端（UI-03、UI-04）
```

### Bad Example

這個範例保留空的檔案系統端，執行的 AI 會以為漏了任務，或自行補上不必要的修改。

```markdown
### 檔案系統端（FS-01、FS-02 讀取）

（本故事無任務）
```
