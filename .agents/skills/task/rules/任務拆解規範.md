# 任務拆解規範

## Rule 1 -- Setup 依 techstack.md 套件安裝清單建立

**強度：MUST**

Setup Phase 只放實作所需的專案骨架與工具鏈。每個 workspace 的設定檔各一個任務，套件名稱與版本必須與 techstack.md「套件安裝清單」完全相同，不得加入清單以外的套件，也不得放入任何商業邏輯。清單中只供測試使用的 workspace、套件、scripts 與設定（如驗收 workspace、測試框架、瀏覽器自動化、`test` script、測試環境設定）一律略過。

### Good Example

這個範例的 frontend 設定檔任務只列建置用的 `vite`，略過清單中只供測試使用的 `vitest`、`jsdom` 與 `test` script。

```markdown
- [ ] T003 [P] 建立 `frontend/package.json`（devDependencies `vite@^6.0.0`；scripts `dev`、`build`）與 `frontend/vite.config.js`：`server.proxy` 將 `/api` 轉發至 `http://localhost:3000`
```

### Bad Example

這個範例照抄清單建立驗收 workspace 與測試套件，tasks.md 混入測試基礎建設，與使用者自己的測試流程重複建置。

```markdown
- [ ] T004 [P] 建立 `e2e/package.json`（devDependencies `@cucumber/cucumber@^11.0.0`、`playwright@^1.49.0`）與 `e2e/cucumber.mjs`
```

## Rule 2 -- Foundational 只放跨故事的阻擋性基礎

**強度：MUST**

Foundational Phase 只能放兩個以上使用者故事都會用到、且不完成就無法開始任何故事的任務，例如設定讀取、資料庫遷移、連線池、路由器、共用元件。只有單一故事使用的模組必須放在該故事的 Phase。

### Good Example

這個範例把所有故事共用的遷移放在 Foundational，只有 US1 使用的檔頭判定放在 US1。

```markdown
## Phase 2：Foundational

- [ ] T011 撰寫 `backend/src/db/migrations/001_init.sql`

## Phase 3：使用者故事 1

- [ ] T035 [P] [US1] 實作 `backend/src/lib/sniff.js`
```

### Bad Example

這個範例把只有 US3 使用的拖放模組提前到 Foundational，US1 被迫等待與它無關的任務，故事也無法獨立交付。

```markdown
## Phase 2：Foundational

- [ ] T019 [P] 實作 `frontend/src/lib/sortable.js`
```

## Rule 3 -- 使用者故事依 spec.md 優先順序各成一個 Phase

**強度：MUST**

每個使用者故事各自成為一個 Phase，依 spec.md 的優先順序（P1、P2…）由前到後排列，Phase 標題沿用 spec.md 的故事名稱與優先順序，第一個故事標示 🎯 MVP。不得合併多個故事或依實作難度重排。

### Good Example

這個範例依 spec.md 優先順序排列，並沿用故事名稱。

```markdown
## Phase 3：使用者故事 1 - 匯入照片並依日期自動分組成相簿（Priority: P1）🎯 MVP

## Phase 4：使用者故事 2 - 在相簿中以平鋪方式預覽照片（Priority: P2）
```

### Bad Example

這個範例因為刪除照片比較簡單就排到前面，MVP 不再是 P1 故事，交付順序與 spec.md 的價值排序不一致。

```markdown
## Phase 3：使用者故事 4 - 從應用程式刪除照片（Priority: P4）

## Phase 4：使用者故事 1 - 匯入照片並依日期自動分組成相簿（Priority: P1）
```

## Rule 4 -- 任務只涵蓋實作

**強度：MUST**

tasks.md 只列產出正式程式碼與設定的實作任務。不得列出單元、契約、整合或驗收（feature、steps）測試任務，不得列出測試輔助、fixture、覆蓋率門檻等測試基礎建設，也不得在實作任務的描述或細項中夾帶「並撰寫測試」「測試寫在…」等測試工作。

### Good Example

這個範例的路由器任務只寫實作內容與完成條件。

```markdown
- [ ] T009 [P] 實作 `backend/src/lib/router.js`：以「方法 + 路徑樣式（`:param`）」比對並解析 path 與 query 參數，未匹配回傳 404
```

### Bad Example

這個範例在實作任務夾帶單元測試，又另列測試 fixture 任務，測試工作被混進實作流程，與使用者自己的測試流程重複。

```markdown
- [ ] T009 [P] 實作 `backend/src/lib/router.js`：…；單元測試寫在 `backend/tests/unit/router.test.js`
- [ ] T007 [P] 建立測試照片 fixture 於 `e2e/fixtures/photos/`
```

## Rule 5 -- 任務描述必須寫出確切路徑與可驗收內容

**強度：MUST**

每個任務描述必須寫出 plan.md「原始碼」中的確切檔案路徑，並寫出可驗收的具體內容：要實作的函式、端點、狀態碼、欄位或文案，取自介面文檔的原值。不得只寫「實作相簿 API」等無法判斷是否完成的描述。

### Good Example

這個範例寫出檔案路徑、路由、參數範圍與錯誤狀態碼，完成與否可以直接判斷。

```markdown
- [ ] T040 [US1] 實作 `backend/src/routes/albums.js` 的 `GET /api/albums`（驗證 `limit` 1～200、`offset` ≥ 0，超出回 400），並註冊至 `backend/src/app.js`
```

### Bad Example

這個範例沒有路徑與具體內容，執行的 AI 不知道要改哪個檔案、做到什麼程度才算完成。

```markdown
- [ ] T040 [US1] 實作相簿列表 API
```

## Rule 6 -- Polish 只放跨故事的實作收尾

**強度：SHOULD**

Polish Phase 應只放橫跨多個故事的實作收尾，例如 lint、format 與建置修正。效能量測、容量種子資料、無障礙掃描、覆蓋率門檻與執行全部測試等驗證工作不列入。

### Good Example

這個範例的 Polish 只做全專案的程式品質收尾。

```markdown
- [ ] T060 [P] 執行 `npm run lint` 與 `npm run format`，修正全專案問題
```

### Bad Example

這個範例把效能量測腳本放進 Polish，驗證工作混入實作流程。

```markdown
- [ ] T061 [P] 實作 `backend/scripts/perf.js`：對 `GET /api/albums` 等端點量測 p95／p99
```

## Rule 7 -- 完成判準寫成可觀察的完成狀態

**強度：MUST**

每個使用者故事 Phase 必須寫一句完成判準，取材自 spec.md 該故事的驗收情境，描述故事完成後在執行中的應用程式裡可以觀察到的操作結果。不得出現「測試」字眼，也不得以測試檔、測試指令或測試通過作為判準。

### Good Example

這個範例描述使用者可以操作並看到的結果，執行者能直接在應用程式中對照。

```markdown
**完成判準**：匯入 10 張分屬 3 個日期的照片後，主頁顯示 3 本以日期命名的相簿、照片總數 10，且每張照片只在其拍攝日期的相簿中
```

### Bad Example

這個範例以測試通過作為判準，沒有測試任務時無從判斷，也把測試工作帶回實作流程。

```markdown
**完成判準**：US1 的契約測試與 `匯入與分組.feature` 全數通過
```
