# 憲法套用規範

## Rule 1 -- 依目錄載入產出物的憲法檔

**強度：MUST**

撰寫、寫回或檢查產出物前，必須讀取 `.claude/constitution/CONSTITUTION.md`，在「目錄」表以「產出物」欄找出本次寫入的產出物，讀取該列「憲法檔」欄的檔案。只套用本次寫入的產出物所屬的憲法檔，不得套用其他產出物的條款；`CONSTITUTION.md` 不存在或目錄沒有該產出物時，沿用 skill 內建規範。不得依記憶或舊對話中的條款撰寫，每次都必須重新讀取。

### Good Example

這個範例在 clarify-over-specs 寫回 spec.md 時，依「產出物」欄找到 specify 的憲法檔，即使寫入的 skill 不是 specify 也照樣載入。

```markdown
寫入產出物：spec.md
目錄列：| spec.md | skills/specify/spec.md | C-SPEC-01、C-SPEC-02 | — |
載入：.claude/constitution/skills/specify/spec.md
```

### Bad Example

這個範例依寫入的 skill 名稱找 `skills/clarify-over-specs/`，找不到就沿用內建規範，寫回時刪除了無障礙一節，違反 C-SPEC-01 卻沒有被發現。

```markdown
寫入產出物：spec.md
尋找：.claude/constitution/skills/clarify-over-specs/ → 不存在
載入：無，沿用內建規範
```

## Rule 2 -- 共通條款只在被引用時生效

**強度：MUST**

除了產出物的憲法檔，必須再讀取該列「引用共通條款」欄列出的每個共通條款；欄位為「—」時不讀取 `shared/`。不得把未被引用的共通條款套用到產出物。

### Good Example

這個範例撰寫 openapi.yaml 時，依「引用共通條款」欄另外載入 C-SH-01。

```markdown
寫入產出物：contracts/openapi.yaml
目錄列：| contracts/openapi.yaml | skills/api-plan/openapi.md | C-API-01、C-API-02 | C-SH-01 |
載入：skills/api-plan/openapi.md、shared/欄位命名風格.md
```

### Bad Example

這個範例撰寫 storage-contract.md 時也套用 C-SH-01，把命名規則表中的 `content_hash` 改成 `contentHash`，與 data-model.dbml 的欄位對不上。

```markdown
寫入產出物：contracts/storage-contract.md
目錄列：| contracts/storage-contract.md | skills/storage-plan/storage-contract.md | C-FS-01、C-FS-02 | — |
載入：skills/storage-plan/storage-contract.md、shared/欄位命名風格.md
```

## Rule 3 -- 憲法條款優先於內建規範

**強度：MUST**

條款與 skill 內建的 Rule、樣板或範例衝突時，以條款為準：條款的「覆寫對象」列出的 Rule 不再適用於條款涵蓋的範圍；「覆寫對象」為「無（增補）」時，條款要求的內容照樣寫入，樣板沒有的段落或列依條款補上，範例與條款不一致時不得照抄範例。條款強度依 MUST、SHOULD、MAY 的語意執行。

### Good Example

這個範例的 C-UI-01 為增補，樣板的狀態表只有四列，仍依條款加上「離線」列。

```markdown
### 狀態

| 狀態   | 呈現                                                                                      |
| ------ | ----------------------------------------------------------------------------------------- |
| 成功   | 顯示房間成員與目前回合。                                                                  |
| 載入   | 顯示「正在載入房間…」。                                                                   |
| 空狀態 | 只有自己在房間時顯示「等待對手加入」。                                                    |
| 錯誤   | 顯示錯誤訊息與「重新整理」按鈕。                                                          |
| 離線   | 頂部顯示「連線中斷，正在重新連線…」；猜測按鈕停用。恢復連線後重新取得房間狀態並移除提示。 |
```

### Bad Example

這個範例因為樣板與範例都只有四種狀態就照抄，C-UI-01 要求的離線狀態沒有寫入，網路中斷時畫面的行為沒有定義。

```markdown
### 狀態

| 狀態   | 呈現                                   |
| ------ | -------------------------------------- |
| 成功   | 顯示房間成員與目前回合。               |
| 載入   | 顯示「正在載入房間…」。                |
| 空狀態 | 只有自己在房間時顯示「等待對手加入」。 |
| 錯誤   | 顯示錯誤訊息與「重新整理」按鈕。       |
```

## Rule 4 -- 檢查腳本的錯誤不得推翻條款

**強度：MUST**

檢查腳本回報的問題，若照腳本修正會違反已載入的條款，必須保留符合條款的內容，並在回報中列出該問題、對應的條款編號與保留理由；其餘問題照常修正。

### Good Example

這個範例保留依 C-TR-02 收斂的版本，並在回報中說明腳本錯誤的來源。

```markdown
check_techstack.py 回報 `vite` 版本 ~8.0.0 與 research.md 的 ^8.0.0 不一致：
依 C-TR-02 保留 ~8.0.0，研究紀錄欄已加註「（版本依 C-TR-02 收斂）」。
```

### Bad Example

這個範例照腳本訊息把版本改回 `^8.0.0`，產出物重新違反 C-TR-02，各成員安裝時又可能拿到不同的次版號。

```markdown
check_techstack.py 回報 `vite` 版本 ~8.0.0 與 research.md 的 ^8.0.0 不一致：
已改為 ^8.0.0。
```

## Rule 5 -- 寫入後逐條核對整份產出物

**強度：MUST**

寫入產出物後，必須依已載入的每條條款逐一核對：先核對「作用位置」是否寫入條款要求的內容，再以條款描述中「不得」「一律」等禁止或限定的寫法掃描整份產出物，作用位置以外出現的違反同樣算違反。違反 MUST 條款時直接修正；偏離 SHOULD 條款時，必須依該條款描述寫明的方式在產出物留下說明。不得只寫出整體結論而不逐條核對，也不得因違反出現在作用位置以外而判定通過。

### Good Example

這個範例核對完作用位置後，再以 C-DATA-01「不得設計成物理刪除」掃描全檔，抓到作用位置以外的 `Ref` 與表 Note。

```markdown
- C-DATA-01（`Table.*` 欄位）：albums、photos 皆含 created_at、updated_at、updated_by、soft_deleted_at。
- C-DATA-01（`## 交易邊界`）：刪除照片改為更新 photos.soft_deleted_at。
- C-DATA-01 禁止事項「不得設計成物理刪除」掃描全檔：
  - `Ref fk_photos_album_id ... [delete: cascade]` 違反 → 移除 cascade，刪除相簿交易改為先軟刪除該相簿的 photos。
  - photos 的 Note「相簿刪除時連帶刪除」違反 → 改寫為軟刪除。
```

### Bad Example

這個範例只核對作用位置就判定通過，`Ref` 上的 cascade 與表 Note 的連帶刪除都不在作用位置內而被放過，實作後刪除相簿會物理刪除照片列，違反條款卻沒有被發現。

```markdown
- C-DATA-01（`Table.*` 欄位）：四個欄位齊全。
- C-DATA-01（`## 交易邊界`）：刪除照片改為軟刪除。
  → 符合所有條款。
```

## Rule 6 -- 憲法條款優先於輸入文件

**強度：MUST**

條款與本次寫入產出物以外的輸入文件衝突時，以條款為準；輸入文件指本次讀取的上游產物（如 plan.md、techstack.md）與前一功能的產出物。產出物必須照條款撰寫，不得以輸入文件的決策或「沿用既有」為由保留違反條款的內容。沿用前一功能的內容落在已載入條款的作用位置內時，必須讀取前一功能的同名產出物，在本次產出物完整寫出符合條款的內容，不得以「詳見前一功能」之類的引用代替。

### Good Example

這個範例的 plan.md 寫「沿用 001 的端點不變」，001 的相簿列表沒有分頁參數，本次 openapi.yaml 仍完整寫出該端點並依 C-API-01 補上分頁參數。

```yaml
paths:
  /api/albums:
    get:
      summary: 列出相簿（沿用 001）
      parameters:
        - $ref: "#/components/parameters/Page"
        - $ref: "#/components/parameters/PageSize"
```

### Bad Example

這個範例以 plan.md 的決策為由保留 001 的寫法，並用引用代替完整內容，列表端點沒有分頁參數，實作照此文件仍違反 C-API-01。

```yaml
paths:
  /api/albums:
    get:
      summary: 列出相簿（沿用 001，詳見 001 openapi.yaml，依 plan.md 不變）
```

## Rule 7 -- 與輸入文件的衝突必須逐項回報

**強度：MUST**

依 Rule 6 以條款取代輸入文件的內容時，必須在回報中逐項列出衝突：輸入文件與位置、衝突內容、條款編號、產出物的處理與後續處理。後續處理對上游產物寫出應回頭修正的 skill，對前一功能的產出物寫出本功能實作需調整的既有實作。不得只寫「已依憲法修正」而不列出位置。

### Good Example

這個範例逐項列出衝突，讀者能直接知道要回頭修正哪個 skill，以及實作要動到哪些既有程式。

```markdown
- techstack.md「資料庫」列：「刪除相簿以 FK CASCADE 連帶刪除照片」與 C-DATA-01 衝突 → photos 外鍵改 restrict，刪除相簿改為軟刪除 → technical-research 修正 techstack.md 與其引用的研究紀錄
- plan.md「結構決策」：「沿用 001 的 albums 表不變」與 C-DATA-01 衝突 → albums 補上四個生命週期欄位 → system-analysis 修正結構決策
- 001 data-model.dbml 的 albums 表：缺 updated_by、soft_deleted_at，與 C-DATA-01 衝突 → 本次產出物已補齊 → 本功能實作需新增遷移補齊既有表
```

### Bad Example

這個範例只寫結論，讀者不知道哪份上游文件與條款衝突，plan.md 與 techstack.md 維持錯誤寫法，後續任務拆解照舊漏掉遷移。

```markdown
- 已依 C-DATA-01 修正資料模型。
```
