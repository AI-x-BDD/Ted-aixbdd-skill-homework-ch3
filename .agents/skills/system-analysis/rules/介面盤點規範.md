# 介面盤點規範

## Rule 1 -- 端點必須是獨立的技術系統

**強度：MUST**

端點是本次需求涉及、可獨立運作或保存資料的技術系統，例如前端、後端、資料庫、檔案系統、手機 App、硬體裝置、雲端服務、第三方服務。必須從 spec.md 的需求與 techstack.md 的技術判斷涉及哪些端點；同一端點內的程式分層（如路由、服務、儲存庫）不得當成端點。

### Good Example

這個範例依 techstack.md 的 MySQL 與 `backend/storage/`，把資料庫與檔案系統各列為獨立端點。

```markdown
端點：前端、後端、資料庫端、檔案系統端
```

### Bad Example

這個範例把後端的程式分層列成端點，卻漏掉保存原始檔與縮圖的檔案系統，Wave 會為分層各開 sub-agent，檔案系統的介面則沒人分析。

```markdown
端點：前端、路由層、服務層、儲存庫層、資料庫端
```

## Rule 2 -- 介面必須歸屬提供它的端點

**強度：MUST**

介面是端點提供給使用者或其他端點使用的部位，所屬端點必須填提供方，不得填使用方。兩個端點之間的連線只能列成一個介面，不得在兩端各列一次。

### Good Example

這個範例把前端呼叫的相簿 API 歸屬於提供它的後端，只列一次。

```markdown
| API-02 | 相簿 API（列表、排序） | 後端 | FR-006、FR-007、FR-013、FR-015、FR-016、NFR-010 |
```

### Bad Example

這個範例在前端與後端各列一次相簿 API，同一份契約會被兩個 sub-agent 各寫一份，內容容易互相矛盾。

```markdown
| UI-05 | 相簿 API 呼叫 | 前端 | FR-007、FR-013 |
| API-02 | 相簿 API（列表、排序） | 後端 | FR-007、FR-013 |
```

## Rule 3 -- 介面粒度依使用部位切分

**強度：SHOULD**

介面應依端點被使用的部位切分：前端依畫面或畫面區塊（如工作區、圖片預覽區），後端依資源分組的 API，資料庫依資料表，檔案系統依儲存區。介面名稱後應以括號列出該部位涵蓋的元素。不應把整個端點列成一個介面，也不應細到單一欄位或單一 HTTP 路徑。

### Good Example

這個範例把前端依畫面切成介面，並以括號列出涵蓋的元素。

```markdown
| UI-01 | 主頁相簿列表介面（相簿卡片、空狀態、拖放與鍵盤排序） | 前端 | FR-007、FR-013 |
| UI-03 | 相簿平鋪預覽介面（縮圖格線、佔位載入、刪除） | 前端 | FR-010、FR-017 |
```

### Bad Example

這個範例把整個前端列成一個介面，依據需求塞滿所有前端需求，無法看出每個畫面對應哪些需求。

```markdown
| UI-01 | 前端介面 | 前端 | FR-001、FR-006～FR-014、FR-016～FR-020 |
```

## Rule 4 -- 介面必須由需求開出

**強度：MUST**

每個介面的依據需求必須列出促使它存在的 FR、NFR 或 SC 編號，連續編號以「～」表示範圍。找不到依據需求的介面不得列入。

### Good Example

這個範例的燈箱介面列出要求放大檢視、返回平鋪與刪除的需求。

```markdown
| UI-04 | 燈箱放大檢視介面（上一張／下一張、返回平鋪、刪除） | 前端 | FR-011、FR-012、FR-017、NFR-007 |
```

### Bad Example

這個範例列出 spec.md 沒有要求的相簿分享介面，Wave 會為不存在的需求安排分析。

```markdown
| UI-05 | 相簿分享介面（分享連結、權限） | 前端 | — |
```

## Rule 5 -- 每條功能需求必須被介面涵蓋

**強度：MUST**

spec.md 的每一條 FR 必須至少出現在一個介面的依據需求中。全域 FR 必須列在所有實際落實它的介面上。

### Good Example

這個範例把要求繁中訊息的全域 FR-020 列在會顯示錯誤、空狀態與載入狀態的三個畫面。

```markdown
| UI-01 | 主頁相簿列表介面（相簿卡片、空狀態、拖放與鍵盤排序） | 前端 | FR-007、FR-020 |
| UI-02 | 匯入對話框介面（選取檔案、進度、略過結果） | 前端 | FR-001、FR-020 |
| UI-03 | 相簿平鋪預覽介面（縮圖格線、佔位載入、刪除） | 前端 | FR-010、FR-020 |
```

### Bad Example

這個範例沒有任何介面引用 FR-020，後續 sub-agent 只依各自介面的依據需求分析，繁中訊息的要求會被所有介面文檔遺漏。

```markdown
| UI-01 | 主頁相簿列表介面（相簿卡片、空狀態、拖放與鍵盤排序） | 前端 | FR-007 |
| UI-02 | 匯入對話框介面（選取檔案、進度、略過結果） | 前端 | FR-001 |
```

## Rule 6 -- 介面 ID 使用端點前綴

**強度：MUST**

介面 ID 固定為 `<端點前綴>-<兩位流水號>`，流水號在端點內從 01 連續遞增。前綴必須依端點類型取下表，任何功能的同類型端點都使用相同前綴，因為 planner-provisioning 以前綴對照負責的 Planner；表中沒有的端點類型自訂一個大寫英文前綴。表格列必須依端點由外而內排列，同一端點的介面相鄰。

| 端點類型   | 前綴  |
| ---------- | ----- |
| 前端       | `UI`  |
| 後端       | `API` |
| 資料庫端   | `DB`  |
| 檔案系統端 | `FS`  |
| 手機 App   | `APP` |
| 硬體裝置   | `HW`  |
| 第三方服務 | `EXT` |

### Good Example

這個範例同一端點共用前綴、流水號連續，且由外而內排列。

```markdown
| UI-01 | 主頁相簿列表介面（相簿卡片、空狀態、拖放與鍵盤排序） | 前端 | FR-007 |
| UI-02 | 匯入對話框介面（選取檔案、進度、略過結果） | 前端 | FR-001 |
| API-01 | 匯入 API | 後端 | FR-001～FR-004 |
| DB-01 | 相簿資料表（含自訂排序） | 資料庫端 | FR-003 |
```

### Bad Example

這個範例為前端自訂 `FE` 前綴並混用全域流水號，planner-provisioning 依前綴找不到 `ui-ux-plan`，會判定缺少並重建一個職責重複的 Planner；資料庫又排在前端之間，Wave 標題無法以範圍引用同一端點的介面。

```markdown
| FE-1 | 主頁相簿列表介面 | 前端 | FR-007 |
| DB-01 | 相簿資料表 | 資料庫端 | FR-003 |
| FE-2 | 匯入對話框介面 | 前端 | FR-001 |
```
